# M12 · Evaluation Harnesses

> **Module question:** How do we know the harness works — and how do we keep knowing it?
> **Cross-cutting threads:** Failure modes · Tradeoff ledger · ADK at a glance
> **Domain spine:** a support agent's eval suite

---

## Opening scene — the change that shipped blind

The team tweaked the support agent's instruction ("be more concise") and shipped it. Two weeks later, a customer complained that the agent now *refused* to answer a routine billing question — a regression nobody caught, because there was no test that would have.

The instruction change had, in M2's terms, made the agent *brittle*: fine on the happy path, broken on a class of inputs the team didn't think to check. And they didn't think to check because **they had no evaluation harness** — no golden cases, no regression gate, no way to *know* that "be more concise" had silently broken "answer billing questions."

This module is the answer to the question every other module has been pointing at: **how do we know?** The evaluation harness is the layer that turns the agent from a thing you *believe* works into a thing you can *verify* works — and, crucially, keep verifying as you change it.

> **Failure mode (the module in one line):** shipping harness changes without a regression signal. An agent is a probabilistic system whose behavior drifts with every instruction, model, and tool change[sculley-hidden-technical-debt](#sculley-hidden-technical-debt) — without evals, every change is a gamble, and you only find out you lost when a customer tells you.

## Why agent evals are not unit tests

Unit tests assert a deterministic pass/fail; agents are probabilistic, so deterministic assertions are "often unsuitable" and the evaluation has to be qualitative.[adk-evaluate-index](#adk-evaluate-index) And, more importantly, **the answer is not the whole story** — outcome-only evaluation "focus[es] exclusively on final outcomes -- ignoring the step-by-step nature of agentic systems."[zhuge-agent-as-a-judge](#zhuge-agent-as-a-judge) An agent can reach the *right answer* through the *wrong path* (called a tool it shouldn't have, leaked data, burned budget). So agent evaluation has two targets:

1. **The trajectory** — the sequence of steps (tool calls, intermediate responses) the agent took. Wrong path is a failure even when the answer is right. (*cf.* §1 of the disagreement section)
2. **The final response** — the quality, relevance, and correctness of the output.

A support agent that *looks up the order, then answers* has a good trajectory; one that *answers from thin air and happens to be right* has a good response and a *terrible* trajectory — because next time it won't happen to be right. **Evaluating only the answer is how you build a harness that works by accident.** The supervision literature makes the asymmetry concrete: "outcome supervision, which provides feedback for a final result" versus "process supervision, which provides feedback for each intermediate reasoning step," with process supervision "significantly outperform[ing]" outcome supervision on MATH.[lightman-process-supervision](#lightman-process-supervision)

> **ADK at a glance:** ADK encodes this split directly. An **eval case** records `user_content`, the expected `tool_uses` (trajectory), expected `intermediate_responses`, and a reference `final_response`.[adk-evaluate-index](#adk-evaluate-index) Eval sets group cases into unit tests (`.test.json`, rapid) and integration evalsets (multi-turn sessions). And **conformance testing** (`adk conformance test`) is the regression mechanism: record a golden baseline, then re-run against it to catch deviations — the "did this change break behavior?" gate, in CI.[adk-evaluate-index](#adk-evaluate-index)

## The eval taxonomy

The criterion set maps cleanly onto the failure classes this course has been tracking:[adk-criteria](#adk-criteria)

| Eval | What it checks | Catches |
|---|---|---|
| **Tool trajectory** (`tool_trajectory_avg_score`) | Exact/in-order/any-order match of tool calls[adk-criteria](#adk-criteria) | Wrong tool, skipped step (M2 class 8) |
| **Response match** (`response_match_score`, `final_response_match_v2`) | Lexical (ROUGE-1)[lin-rouge](#lin-rouge) or *semantic* match to a reference[zhang-bertscore](#zhang-bertscore) | Wrong answer (class 1) |
| **Rubric-based quality** (`rubric_based_*`) | LLM-judged attributes you define ("concise," "correct order")[kim-prometheus2](#kim-prometheus2), [ye-flask](#ye-flask) | Quality where no single reference exists (class 7) |
| **Groundedness** (`hallucinations_v1`) | Each sentence supported by the context[adk-criteria](#adk-criteria) | **Hallucination (class 1)** — the big one[niu-ragtruth](#niu-ragtruth) |
| **Safety** (`safety_v1`) | Harmlessness | Safety violations (M15)[mazeika-harmbench](#mazeika-harmbench) |
| **Multi-turn success / trajectory** (`multi_turn_*`) | Goal completion and path quality over a session[yao-tau-bench](#yao-tau-bench) | Drift, wrong paths (class 4) |

Notice two things. First, **`hallucinations_v1` is the criterion this entire course has been circling**: it segments the response into sentences and validates each against context — `supported` / `unsupported` / `contradictory` (*cf.* §7) — which is *exactly* the citation/entailment check from M5, now as a first-class eval. That form is well owned: decomposing generated text into checkable units and asking whether each is supported by a source is the mechanism behind FActScore[min-factscore](#min-factscore), reference-free RAG faithfulness[es-ragas](#es-ragas), the standardized factual-consistency comparison,[honovich-true](#honovich-true) and sentence-level NLI checking.[laban-sumac](#laban-sumac) Second, the criteria split into **deterministic** (tool trajectory, ROUGE — fast, cheap, CI-friendly) and **LLM-judged** (semantic match, rubrics, groundedness — flexible but probabilistic and model-dependent). Choosing which is a *cost-vs-power* decision, and it's the entry point to the judge problem.

## The judge problem

When the criterion is "semantic match" or "rubric satisfied," *who* judges? A model — **LLM-as-a-judge** — with the same failure modes as the model being judged:[zheng-judge-mtbench](#zheng-judge-mtbench)

- **Sycophancy** (class 2) — the judge agrees with a confident or well-formatted answer. (Careful with the name: sycophancy is owned as agreement with the *user's* stated view,[sharma-sycophancy](#sharma-sycophancy) while a judge favoring a confident, well-formatted answer is the **verbosity / style bias** of the judge itself.[zheng-judge-mtbench](#zheng-judge-mtbench) (*cf.* §2 of the disagreement section)
- **Position/order bias** (class 5) — the judge's verdict flips on phrasing; ranking "can be easily hacked by simply altering their order of appearance in the context."[wang-fair-evaluators](#wang-fair-evaluators)
- **Brittleness** (class 3) — the judge encodes your test set's shortcuts (see "overfitting" below).[dwork-adaptive-holdout](#dwork-adaptive-holdout)

The mitigations are structural, not rhetorical:

1. **Rubrics over vibes.** "Is the response good?" is a vibe; "does it state the amount, cite the order tool, and not fabricate a price?" is a rubric the judge can actually check. ADK's rubric-based criteria make this the unit of judging.[adk-criteria](#adk-criteria) The literature's versions of the same move are form-filling chain-of-thought prompts,[liu-geval](#liu-geval) skill-set decomposition,[ye-flask](#ye-flask) and open evaluators that score against user-supplied criteria.[kim-prometheus2](#kim-prometheus2)
2. **Majority vote + sampling.** The judge is sampled `num_samples` times; a majority vote smooths single-sample noise.[adk-criteria](#adk-criteria) The result is borrowed from *reasoning*, where a unique correct answer exists;[wang-self-consistency](#wang-self-consistency) the bias-side fix is a **jury** of diverse models rather than more draws from one.[verga-juries](#verga-juries), [chan-chateval](#chan-chateval)
3. **Judge independence.** The judge should be a *different* model/setting than the agent, so it doesn't share the agent's blind spots — judges demonstrably favor their own generations.[panickssery-self-preference](#panickssery-self-preference)

And here is where the discussion-thread material (its §6) lands, because it *is* the judge architecture:

### The verification tier: surface, joint, or layered?

A groundedness/entailment check can be built three ways (from the discussion):

- **Surface (single-chunk):** "is this claim entailed by *this* chunk?" — cheap, fast, catches the common case, but *fails on derived/multi-hop answers* (it flags a correct derived answer as unsupported). This is the granularity the NLI summarization work operates at — "segmenting documents into sentence units and aggregating scores between pairs of sentences."[laban-sumac](#laban-sumac)
- **Joint-source:** "does the answer follow from *all* cited sources together?" — handles derivation, but expensive and itself error-prone (more context → more judge failure surface), which is exactly the regime where long-context use degrades.[liu-lost-in-the-middle](#liu-lost-in-the-middle), [du-context-length-alone](#du-context-length-alone)
- **Layered/routed:** surface first (cheap gate), escalate only `neutral` results to joint-source; high-consequence claims go straight to joint. This is a *cascade*, and the LLM-era owner of that shape is FrugalGPT[chen-frugalgpt](#chen-frugalgpt) with learned routing as its refined form.[ong-routellm](#ong-routellm)

**The architecture decision is layered/routed** — surface always, joint on escalation — for the same reason as every other tiered design in this course: spend the expensive check only where the cheap one is ambiguous. (That reasoning, and the surface/joint/layered vocabulary itself, is the course's synthesis, not a finding.[own-synthesis](#own-synthesis)) And the same caveat applies: start surface-only, measure false positives, add the escalation tier when data says so.

> **Tradeoff (the ledger entry):**
> - **Deterministic vs. LLM-judged.** Deterministic criteria (trajectory, ROUGE) are fast and CI-friendly but brittle; LLM-judged criteria are flexible but probabilistic and expensive. Use deterministic for regression, LLM-judged for *quality* — which is also ADK's own recommendation for CI.[adk-evaluate-index](#adk-evaluate-index) The honest caveat: all of these metrics are proxies whose agreement with human judgment is the thing being measured in the first place.[honovich-true](#honovich-true)
> - **Verification vs. cost.** Every eval run costs tokens and latency. Tier it: cheap deterministic gates in CI, expensive judges on release candidates — a cost decision, on the evidence of the cascade work.[chen-frugalgpt](#chen-frugalgpt)
> - **Coverage vs. overfitting.** More eval cases catch more failures — until your eval set *becomes* the shortcuts (below): a holdout reused for many decisions decays.[dwork-adaptive-holdout](#dwork-adaptive-holdout)

## Honest measurement: what evals cannot tell you

The module's humility section, because over-trusting evals is its own failure:

1. **Evals measure what you test, not what matters.** A suite with no billing-policy cases cannot catch a billing-policy regression (M2's Example A, verbatim). Held-out accuracy "often overestimates the performance of NLP models";[ribeiro-checklist](#ribeiro-checklist) and pipelines can "return many predictors with equivalently strong held-out performance in the training domain" that "behave very differently in deployment domains."[damour-underspecification](#damour-underspecification)
2. **Evals overfit.** If you tune the agent until the suite passes, the suite now encodes *your* shortcuts — "reusing a holdout set adaptively multiple times can easily lead to overfitting to the holdout set itself,"[dwork-adaptive-holdout](#dwork-adaptive-holdout) and "optimizing [a proxy's] value too much can hinder ground truth performance, in accordance with Goodhart's law."[gao-reward-overoptimization](#gao-reward-overoptimization) The public-benchmark version is now documented: leaderboards drift toward "overfitting to Arena-specific dynamics rather than general model quality."[singh-leaderboard-illusion](#singh-leaderboard-illusion) The fix is the **production→eval flywheel**: pull real, *failed* cases from production into the eval set, so the suite grows toward the true failure surface, not away from it.[unsupported](#unsupported)
3. **Evals can't prove safety.** A passing safety eval means "didn't violate *these* cases," not "can't violate any" (M14/M15 own that gap). Robustness evaluation is itself a research problem — "correctly evaluating defenses against adversarial examples has proven to be extremely difficult," and "most papers that propose defenses are quickly shown to be incorrect"[carlini-adversarial-robustness](#carlini-adversarial-robustness) — and the assurance literature's answer is not a bigger suite but an explicit argument: "a structured rationale that AI systems are unlikely to cause a catastrophe."[clymer-safety-cases](#clymer-safety-cases)
4. **The judge is a model.** Every LLM-judged metric inherits the judge's failure modes — so a "100% grounded" score is a *probabilistic* claim, not a certificate. Measured on objectively checkable preference pairs, strong judges perform "just slightly better than random guessing."[tan-judgebench](#tan-judgebench)

The honest posture: **evals raise the cost of being wrong; they don't eliminate wrongness.**[own-synthesis](#own-synthesis) They're a regression net, not a proof — and the net's value is entirely in *how you grow and gate with it*.

## Worked example: the support agent's eval suite

The domain spine, assembled from the whole course (illustrative — these cases restate this course's own failure taxonomy, and the cross-references point at the modules that own them):

- **Golden cases** (deterministic): "where's my order" → must call `lookup_order`, not `refund`; `tool_trajectory_avg_score` exact.[adk-criteria](#adk-criteria)
- **Groundedness** (`hallucinations_v1`): every policy answer must be supported by the retrieved policy chunk — the Air Canada case (M2), now a *failing test the agent must pass*.[niu-ragtruth](#niu-ragtruth)
- **Rubric** (`rubric_based_final_response_quality_v1`): "does not fabricate a refund amount not returned by the order tool" (the M6 exercise's rule 3, as a rubric).[kim-prometheus2](#kim-prometheus2)
- **Drift test** (multi-turn): the $400 refund request at message 39 must still escalate (M2 Scenario C, as a regression) — the reliability form of this is **pass^k** over repeated trials, not a single green run.[yao-tau-bench](#yao-tau-bench)
- **Gate**: deterministic criteria in CI every PR; judges on release candidates; failed production cases flow *back* into the set.[adk-evaluate-index](#adk-evaluate-index)

The point: the suite is not a random pile of prompts — it is the *failure taxonomy of this course, operationalized*. Each failure class (hallucination, drift, sycophancy, wrong tool) has a corresponding eval case that would catch it.

## Design exercise

> *Paper-based. Think, then write.*

**Task.** Design the eval harness for an agent you know (or the support-agent brief).

1. **Name the failure classes to catch.** From M2's nine, pick the four your agent is *actually* exposed to, and write one eval case per class — user input + the check that would catch it.
2. **Split trajectory from response.** For one case, write the expected `tool_uses` (trajectory) *and* the reference response — and explain what each catches that the other misses.[lightman-process-supervision](#lightman-process-supervision)
3. **Choose the criteria.** Map each case to a criterion (deterministic vs. LLM-judged), and justify the choice in one line. Which cases deserve a *rubric* (no single reference) vs. a *reference match*?[adk-criteria](#adk-criteria)
4. **Design the judge tier.** For the groundedness check, state whether you'd run surface-only or layered/routed, and why — using the false-positive argument. Then say what would have to be *measured* to justify the escalation tier, given that the cascade evidence is about cost.[chen-frugalgpt](#chen-frugalgpt)
5. **State the blind spots.** Name three things your suite *cannot* catch (the "what evals can't tell you" list), and the *non-eval* control for each (M14/M15, human review, etc.).[clymer-safety-cases](#clymer-safety-cases)
6. **Write the gate.** Which evals run in CI on every PR, which on release, and what flips the flywheel (production failures → eval cases)?[unsupported](#unsupported)

**Why this exercise matters.** Every previous module has *assumed* you could verify a fix. This module is the verification itself. If you can name the failure classes, map them to evals, and know what the evals *can't* see, you've closed the loop the whole course has been building toward — and you can finally answer the question from M1's opening scene: *"how would anyone ever know it went wrong?"*

## Where the literature disagrees with this module

The claims above are directionally right and mostly well owned — the trajectory/response split is the field's own framing, and the metric family the module names has real papers behind it. But three of the module's load-bearing moves are weaker than the prose suggests: two labels are borrowed from the wrong literature, one architecture decision is justified with a *cost* result, and the flywheel fix has no measured support at all. Checked against the docs rather than against the module's prose, the framework details also need corrections. Recording these is the same discipline this module teaches — trace the claim to its source, and flag where the source says "maybe."

### 1. Trajectory matching is the bluntest instrument in the suite — "wrong path is a failure" is too strong

The module says a wrong path "is a failure even when the answer is right," and the ADK criterion it points at compares trajectories **exactly**.[adk-criteria](#adk-criteria) Two problems:

- **Legitimate paths are not unique.** Real agents reach the same correct state by different routes; a golden one-shot trajectory is a reference *you* chose. The same ADK doc hedges for exactly this reason, offering `EXACT`, `IN_ORDER`, and `ANY_ORDER`, plus a *rubric-based* tool-use criterion for cases "where multiple tool-use paths could lead to a similar final answer but only one path is considered correct."[adk-criteria](#adk-criteria)
- **The strongest multi-turn benchmark does not score the path at all.** τ-bench measures whether the interaction leaves the domain in the right end state, and adds `pass^k` because the real question is *reliability across trials*, not conformance to one golden transcript: "we also propose a new metric (pass^k) to evaluate the reliability of agent behavior over multiple trials," reporting "pass^8 <25% in retail."[yao-tau-bench](#yao-tau-bench)
- The step-level judging case is real but narrower than the module states: the argument is that outcome-only evaluation "focus[es] exclusively on final outcomes -- ignoring the step-by-step nature of agentic systems,"[zhuge-agent-as-a-judge](#zhuge-agent-as-a-judge) and the process-supervision result is a training result on MATH, not a claim that any deviation from a recorded path is a defect.[lightman-process-supervision](#lightman-process-supervision)

**Consequence.** Keep the split — trajectory *and* response — but teach it as **two families of check with different false-positive modes**: exact trajectory match is a regression tripwire (cheap, brittle, right for high-precision workflows), and rubric-based or end-state checking is what you use where several good paths exist. Add `pass^k`-style repetition to any case whose value is reliability, because one green run on a sampling system is not evidence.

### 2. "Sycophancy" is the wrong name for the judge-side bias

The module's judge-bias bullet list assigns **sycophancy** to "the judge agrees with a confident or well-formatted answer." The literature owns that word for something else:

- Sycophancy is **user-directed** agreement: "human feedback may also encourage model responses that match user beliefs over truthful ones, a behaviour known as sycophancy," and "both humans and preference models (PMs) prefer convincingly-written sycophantic responses over correct ones a non-negligible fraction of the time."[sharma-sycophancy](#sharma-sycophancy) That second clause *is* relevant to judges — but as a preference-model result, not as "the judge likes confident answers."
- The failure the module actually describes is a judge-side **style/verbosity** effect, named in the judge taxonomy itself: "we examine the usage and limitations of LLM-as-a-judge, including position, verbosity, and self-enhancement biases."[zheng-judge-mtbench](#zheng-judge-mtbench)

**Consequence.** Relabel the bullet. Keep sycophancy where it belongs (the *agent* agreeing with the user — an M2 class 2 failure with a first-class citation), and give the judge bullet its own name: **verbosity / style bias**, with position bias and self-preference as its siblings. As written, the list teaches a term with the wrong owner.

### 3. Majority vote fixes noise, not bias

"Sampled `num_samples` times; a majority vote smooths single-sample noise"[adk-criteria](#adk-criteria) is accurate about what sampling does — and the module then treats it as a *bias* mitigation. The source of the technique is a reasoning result with a unique correct answer to converge on: self-consistency "first samples a diverse set of reasoning paths ... and then selects the most consistent answer."[wang-self-consistency](#wang-self-consistency) A judge's verdict on subjective quality has no such ground truth to concentrate on, so averaging samples of *the same judge* reproduces its bias more precisely.

- The bias-side fix in the literature is **composition**, not repetition: a panel of smaller diverse models "outperforms a single large judge, exhibits less intra-model bias due to its composition of disjoint model families, and does so while being over seven times less expensive."[verga-juries](#verga-juries) Multi-agent debate judges are the same instinct applied to discussion rather than voting.[chan-chateval](#chan-chateval)
- And judges are not reliable enough for the vote to be the load-bearing part: on objectively checkable pairs, "many strong models (e.g., GPT-4o) perform just slightly better than random guessing."[tan-judgebench](#tan-judgebench)

**Consequence.** Keep `num_samples` — it is free variance reduction — but say what it buys: *sampling the same judge reduces its noise, not its bias.* Pair it with a jury of diverse judges (or a different judge family), and treat judge accuracy itself as something to measure before trusting a verdict.

### 4. The tiered-verification argument is a cost argument, and the accuracy half is unmeasured

This is the module's most confident design decision, and it is two claims welded together — one sourced, one not:

- **Sourced:** the cascade. FrugalGPT "learns which combinations of LLMs to use for different queries in order to reduce cost and improve accuracy,"[chen-frugalgpt](#chen-frugalgpt) and the refined routing form "dynamically select[s] between a stronger and a weaker LLM" to "optimize the balance between cost and response quality."[ong-routellm](#ong-routellm) Both are **cost** results on the *same* task being routed.
- **Unsourced:** the module's stated motivation for escalation is an **error-rate** claim — surface-only "flags a correct derived answer as unsupported," so joint-source is the fix. No located source measures whether adding a joint-source tier *reduces* that false-positive rate on derived answers. And the multi-hop verification literature is a warning, not an endorsement: verification over several documents is a dataset-sized hard problem — claims whose evidence must be "extract[ed] from as many as four English Wikipedia articles,"[jiang-hover](#jiang-hover) questions requiring "finding and reasoning over multiple supporting documents,"[yang-hotpotqa](#yang-hotpotqa) and multi-hop benchmarks that models partly beat "via shortcuts."[trivedi-musique](#trivedi-musique) Joint-source is not automatically the accurate tier; it is the *expensive* one.
- The "more context → more judge failure surface" half is directionally supported but at one remove: the measurements are of task performance in long contexts — performance "significantly degrades when models must access relevant information in the middle of long contexts,"[liu-lost-in-the-middle](#liu-lost-in-the-middle) and degrades "even when models can perfectly retrieve all relevant information" purely from length.[du-context-length-alone](#du-context-length-alone) Whether *the judge* gets worse on longer evidence spans is the module's extrapolation, and it is the right thing to measure next.

**Consequence.** Keep layered/routed as the architecture — but present it as a **cost allocation with a hypothesis attached**, and write the missing experiment into the design: hold a set of derived answers with known-good joint support, run surface-only and joint-source on both, and report the false-positive rate each way. Until that number exists, "joint on escalation" is a design bias, not a measured win.

### 5. "Evals overfit" is well supported; the production→eval flywheel is not

The diagnosis is owned and strong:

- Holdout reuse: "reusing a holdout set adaptively multiple times can easily lead to overfitting to the holdout set itself."[dwork-adaptive-holdout](#dwork-adaptive-holdout)
- Proxy over-optimization: "because the reward model is an imperfect proxy, optimizing its value too much can hinder ground truth performance, in accordance with Goodhart's law."[gao-reward-overoptimization](#gao-reward-overoptimization)
- The public-benchmark version, including unequal access to private variants, producing "overfitting to Arena-specific dynamics rather than general model quality."[singh-leaderboard-illusion](#singh-leaderboard-illusion)
- With one honest *cf.*: the canonical test-set-reuse study for ImageNet found accuracy drops on rebuilt test sets but attributed them to harder examples rather than to adaptivity — "our results suggest that the accuracy drops are not caused by adaptivity."[recht-imagenet](#recht-imagenet) Cite it for *test sets decay*, not for a measured adaptive-overfitting term.

The **fix**, though, is asserted rather than sourced: no located source measures a production→eval flywheel improving the true failure surface, and none measures the turning point the module names ("until your eval set *becomes* the shortcuts"). Pulling production failures into the suite is a reasonable engineering practice, and its nearest located instrument is a paywalled production-ML testing rubric that is not entered here — which is exactly the situation the unsupported bucket exists for.[unsupported](#unsupported)

**Consequence.** Keep the flywheel as a *policy* with its rationale spelled out — and be honest that it is a policy. The measurable version: track the fraction of eval cases that originate from production failures, and check that suite pass-rate and production incident-rate move together. If they diverge, the suite is being trained against, not grown toward the failure surface.

### 6. A passing safety eval is weaker than the module admits — and the answer is not a bigger suite

The module's humility here is right and worth sharpening with the strongest available evidence:

- Evaluating robustness is a research problem in its own right: "correctly evaluating defenses against adversarial examples has proven to be extremely difficult," and "most papers that propose defenses are quickly shown to be incorrect."[carlini-adversarial-robustness](#carlini-adversarial-robustness)
- Standardized safety evaluation exists precisely because ad-hoc suites disagree with each other: HarmBench is "a standardized evaluation framework for automated red teaming," built to compare attacks and defenses on common ground.[mazeika-harmbench](#mazeika-harmbench)
- The assurance literature reframes the goal: what a deployment needs is a "safety case," "a structured rationale that AI systems are unlikely to cause a catastrophe," organized from enumerated argument types[clymer-safety-cases](#clymer-safety-cases) — not a green test run.

**Consequence.** Keep "a passing safety eval means *didn't violate these cases*." Add the consequence the module leaves implicit: the *non-eval* controls (capability boundaries, human approval, red-teaming) are not a fallback for a weak suite — they are the actual assurance mechanism, and the suite is one input to it. Also name the sampling problem: an eval suite is a sample of the harm space, and the adversary chooses the unsampled region.

### 7. "Hallucination is the big one" — and the label set is bigger than the module's

The module presents `hallucinations_v1` as segmenting sentences and validating each as `supported` / `unsupported` / `contradictory`. That is the right shape — sentence-level, source-grounded validation is exactly what FActScore[min-factscore](#min-factscore), reference-free RAG faithfulness,[es-ragas](#es-ragas) the standardized comparison of consistency metrics,[honovich-true](#honovich-true) and sentence-level NLI checking[laban-sumac](#laban-sumac) each own a piece of. Two corrections:

- The criterion's actual label set has **five** values, not three: each sentence is "labeled as `supported`, `unsupported`, `contradictory`, `disputed` or `not_applicable`," and the score is "the percentage of sentences that are `supported` or `not_applicable`."[adk-criteria](#adk-criteria) The `not_applicable` half matters in practice: non-claims (greetings, formatting, hedges) count toward a passing score, so a high groundedness number is *percentage of non-claims and supported sentences*, not percentage of verified facts.
- The judge doing the validating is the weak link, not the typology: entailment-style metrics are the strongest family available and still imperfect,[honovich-true](#honovich-true) RAG systems still "present unsupported or contradictory claims to the retrieved contents"[niu-ragtruth](#niu-ragtruth) even when the retrieved evidence is present, and judges on objective pairs can be near chance.[tan-judgebench](#tan-judgebench)

**Consequence.** Use the three-label story as the *mechanism*, cite who owns it, and then teach the two facts the module omits: the score's denominator includes non-claims, and "100% grounded" is a claim about a probabilistic judge over a specific context. Also prefer the corpus-level framing the RAG-hallucination work uses — word/span-level annotation over thousands of responses[niu-ragtruth](#niu-ragtruth) — over the intuition that the metric settles the question.

### 8. Framework claims: verified against the docs, with four corrections

Checked against the live ADK documentation and the DSH checkout rather than against the module's prose:

- **Confirmed exactly.** Eval cases carry `user_content`, `tool_uses`, `intermediate_responses`, and `final_response`; test files are `.test.json` and evalsets hold multi-session interactions; `adk conformance test` compares against a recorded "golden baseline."[adk-evaluate-index](#adk-evaluate-index) Criterion names, the `EXACT`/`IN_ORDER`/`ANY_ORDER` match types, `num_samples` majority voting, and the "use `tool_trajectory_avg_score` and `response_match_score` in CI/CD" recommendation are all as the module states.[adk-criteria](#adk-criteria)

- **Correction 3 — `hallucinations_v1` has five labels, and counts non-claims as grounded** (see §7).[adk-criteria](#adk-criteria)
- **Correction 4 — the DSH sentence is a misquote, and `guard`/`feedback` are not eval machinery.** The documentation reads "Fork, resume, transcripts, telemetry, and persistence all derive from these durable settlements," not "from this stream";[dsh-architecture](#dsh-architecture) the quote above has been corrected in place.
