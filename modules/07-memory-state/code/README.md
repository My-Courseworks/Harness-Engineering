# M7 code: seven memory types, one card-care desk, two frameworks

A customer-support agent for **Kestrel Card**, a fictional card issuer, built twice: once on **Google ADK** and once on **LangGraph**. Both share the same scenario, the same versioned procedure, the same bank systems and the same scheduler. Each puts the module's seven memory types ([README](../README.md#the-memory-taxonomy-seven-types-two-axes-four-scopes)) where that framework's own primitives put them.

Every claim below is backed by live runs against DeepSeek, from empty stores, in three forms:
- **The scripted scenario:** a month in the life of the desk.
- **An adversarial and unscripted suite** built from five rounds of an interviewer's attempts to break the design, plus probes written each round against my own code. Each round's new probes were first run against the previous round's code, unchanged, to show the break (the `adversarial-baseline*` folders; a probe written after a round's baseline has its own `adversarial-before-*` folder, run on the commit just before its fix).
- **Held-out suites, run once and blind.** Round 4's was written by a separate agent before any round-4 fix existed, committed unread and pushed on its own (`cfe3eca`) before the first fix commit (A24). Round 5's, for the one-time-code step-up, was written the same way before the feature existed (`fe86719`, A25). Round 6's, for what the round-5 review broke, was committed unread and pushed alone before any fix commit (`7e51ce1`), with the limits its author reported (A26).
- **Each claim about the one-time code has a check that has been seen to fail.** A mutant puts one defect back and the probe written for it is run once (`evidence/mutants/`; the table is in the write path, step 2).
- **The stores themselves, read after every step** by a scanner that shares no code with the masker. In round 5 that scanner turned out to have two blind spots of its own; both are closed, and what closing them showed is in [Evidence](#evidence-what-was-run-and-what-failed).

Offline measurements back what a live run cannot sample densely: the card-data masker (recall and precision on tuning corpora, two held-out corpora and two fuzzers, one of them written independently), and the LLM judge (agreement with independent labels on transcripts the agents wrote).

See [Evidence](#evidence-what-was-run-and-what-failed).

## The scenario

Kestrel's card-care desk serves four logged-in cardholders over one simulated month, plus a jump past the retention windows:

| when (simulated) | who | what happens | memory types exercised |
|---|---|---|---|
| Nov 9 | Priya | sets a travel notice (Lisbon, to Nov 30) and email as contact channel; disputes "the later" of two StreamMax charges; asks what a chargeback is; asks the FX fee | semantic, working, external, prospective, parametric, episodic |
| Nov 12 | Priya | new session: "what did we sort out last time?"; "is it resolved?"; "how will you contact me?"; switches to SMS (re-verifies) | episodic, external, semantic, working |
| Nov 12 | Marco | asks what is on file for him; asks about "a customer called Priya"; disputes a $240 gym renewal | semantic + episodic leakage, prospective approval |
| Nov 18, Nov 20 | back office | two separate decisions: each cancelled-subscription dispute is rejected for `NO_CANCELLATION_PROOF` | (system of record) |
| Nov 19 | scheduler | Priya's follow-up fires and texts her (the channel she chose *after* the record was written) | prospective, semantic |
| Nov 20 | Priya | "why was it rejected?"; asks for a reminder on Nov 29; asks for a recap across conversations | external, prospective, episodic |
| Nov 22 | scheduler + ops | Marco's follow-up fires; the agent's draft is held; a reviewer approves *that text*, which is then sent once | prospective |
| Nov 23 | Marco, then reviewer | Marco asks why he was rejected; the recurring outcome (two customers, two decisions) is promoted: model draft → reviewer edit → v2 | procedural |
| Nov 24 | Dana, then Eli | Dana's identical dispute under v2 (asks for the reference first); a retraction drill restores v1 and lists Dana's conversation for review; Eli's identical dispute under v1 as the control | procedural |
| Nov 29 | scheduler | Priya's reminder fires | prospective |
| Dec 3 | Priya | travel notice has expired; sets and then deletes a new one; pastes a full card number | semantic (staleness, deletion), guard |
| Dec 3 | Priya, then the bare model | asks Kestrel's late fee, which no document holds: the agent declines, the bare model invents one | parametric |
| Jun 15 2027 | maintenance, Priya | episodes (180 days) and transcripts (30 days) past retention are deleted; "what did we talk about last time?" | episodic, working (forgetting) |

The domain was picked because every memory type has a non-contrived job in it, and because its failure modes are the module's ones with real consequences. A stale travel notice causes wrong fraud decisions. Leaking another cardholder's case is a privacy breach. A follow-up that never fires, or fires after the customer cancelled it, is a broken promise. A stored card number is a PCI incident.

## Where each memory type lives

| type | the module's framing | ADK | LangGraph |
|---|---|---|---|
| **Working / in-context** | the session, re-sent every turn, plus a scoped scratchpad; bounded | `Session` events in `DatabaseSessionService` (SQLite), re-sent up to 8 customer turns (`window_working_memory`, a `before_model_callback`), each message capped at 4,000 characters. Session state: `identity_verified_at`, `first_active_at`, `last_active_at`, `reflected_turns`, `episodes_written`; `user:*`; `app:*`; `temp:now` (trimmed before persistence). Not session state: failed verifications (rows in the bank) and the session's kind (passed in by whoever starts it) | thread messages in `SqliteSaver`, re-sent up to 8 customer turns (`windowed_messages` in the agent node), same cap; the same fields as graph-state channels, `identity_verified_at` with a reducer so parallel calls cannot crash the step; `TurnContext.now` and the session id as per-invocation `context`, never checkpointed (the `temp:` analog). Threads have no owner, so the harness names them `<user>:<session>` |
| **Semantic** | facts, verified, timestamped, scoped, overwritten not appended | `user:contact_channel`, `user:travel_notice` written through `tool_context.state`, preloaded into the instruction by an `InstructionProvider` | `SqliteStore` namespace `("facts", user)`, key = fact name, `put()` overwrites, preloaded into the system prompt by the agent node |
| **Episodic** | what happened, as validated reflections, searched on demand | `EpisodeMemoryService(BaseMemoryService)`: `add_memory` / `search_memory` / `delete_memory` on SQLite + local embeddings, recalled by ADK's built-in `load_memory` | `SqliteStore` namespace `("episodes", user)` with a sqlite-vec index, recalled by a `load_memory` tool |
| **Procedural** | the versioned instruction, not a store; promotion needs evidence, a reviewer and a retraction path | the `InstructionProvider` reads the active version each turn | the agent node reads the active version each turn |
| **External / retrieval** | the store + a retriever; exact lookup for specific facts, vector search for related text | tools: `find_transactions`, `get_case_status` (exact SQL, scoped by `tool_context.user_id`), `search_policy` (embeddings) | the same tools, scoped by `runtime.context.user_id` |
| **Parametric** | the unmanaged floor | the DeepSeek weights, via `LiteLlm` | the DeepSeek weights, via `ChatDeepSeek` |
| **Prospective** | a scheduler the harness owns, never the memory store; five fields; "until done or cancelled" | `cardcare/scheduler.py`. Written by `file_dispute` and `schedule_reminder` (a local time and an IANA zone, at most 90 days ahead; one reminder per customer per *local* day, a unique index), read by `list_my_followups`, cancelled by `cancel_reminder`. Each record carries the memory generation it was written in. Fired by `tick` into a fresh session that has only read tools and `notify_customer`; one message per follow-up is a unique index on the outbox; a held draft is approved by a person, and a message carrying a masking token is never sent | the same scheduler, fired into a fresh thread with the same reduced tool set |

The procedure, the bank, the scheduler and the write-path rules are shared code. That is deliberate: procedural and prospective memory are framework-independent by the module's own definition. The differences between the two agents are therefore all about *where state lives*, which is the comparison worth making.

### The write path, end to end

1. **Masking** (`cardcare/masking.py`). Card data is found by what a card number *is*, not by listing formats.
   - The text is NFKC-normalised; every Unicode digit becomes ASCII, every space and dash is mapped, zero-width characters are dropped. Spoken numbers become digits too: "five" 5, "oh" 0, "fifteen", "fifty-five", "double five", merged into groups ("fifty-five fifty-five"); a lone number word that counts ("the first **four** are") is not a digit.
   - Digit tokens that are never card data get a role: identifiers (`C-5001`, `CN-77812`), amounts (`$240`, `39 euros`, `15.99`), clock times, dates, phone numbers, a ZIP after "zip", a last four after "ending" or "last four", a year after "since".
   - A card number is any sequence of the remaining digit groups, whatever sits **between** them (newlines, list markers, sentences, any number of words) and whatever sits **before** them in the same run (a code, PIN, expiry or order number typed just before the number: "CVV: 737 5555 5555 5555 4444", "order 12345, 5555 5555 5555 4444"; round 5, after the round-4 review found that the first run was always taken whole). It must hold 13-19 digits, start with a card network's prefix, pass Luhn and be grouped like a card. One group per line, a dictated "the first four are …, the next four are …", spelled pairs and Arabic-Indic digits are all the same number. A single written run with a card prefix and card grouping is masked even when Luhn fails: a mistyped card. A run after a reference label ("order", "tracking", "booking ref") is that reference, unless a card number ends it; a tracking number whose tail happens to pass Luhn stays one number because its tail is grouped like the rest of it. A number never continues through "cvv" or "exp": what follows those words is the code or the expiry (round 5: "4111111111111111, cvv 1 8 1" had matched as an 18-digit number when it passed Luhn by chance, cutting the code in two).
   - **A complete card number wins over a role** (round 6; the round-5 review's blocker 2.4). The roles in the bullet above are readings of one token by its neighbours, and three of them could take a group out of a number: `exp Dec 29 5555 5555 5555 4444` read the first 5555 as the date's year, `Visa-4111 1111 1111 1111` and `Card5555 …` read the first group as an identifier, `… 4444 days ago` read the last as an amount; twelve digits were left, which are no card, and the number was stored raw. After the roles are given, written tokens joined by separators only are read once more without them (`_release_card_groups`): a window that is 13-19 digits with a card prefix, Luhn-valid and grouped like a card is a card, and a soft role inside it is dropped. `fuzz-v2` asks the question of every role that can hold a group (date, identifier, amount, phone), 150 renderings each, with a keep family for the same roles at their ordinary job. The reverse case is a count: six or more tokens that count upwards past nine are a numbered list's own numerals, not a card (a 13-line list read as `2345678910111213`, Luhn-valid, and the reply masker removed its lines 2 to 13).
   - **A list's own numbers are not card digits** (round 6; found by the blind held-out run after the count rule above had been called enough). Numerals that number a list (`3.`, `4)`, `(5)`, `6:`; three or more counting up by one) get a role of their own, and in an item that has words a one- or two-digit number is that item's own ("7. Carry 3 adapters"). The count rule only knew a list of bare numerals: ADK's reply to "a numbered checklist, 1 to 16" lost its lines 3 to 14 in the blind run, and 74 of 150 generated checklists whose items hold other numbers were damaged, typed by a customer or written by the model. A card number typed as a numbered list ("1. 5555 / 2. 5555 / …") keeps its groups, which are three digits or more.
   - **The first complete number from a start is the number.** A later run does not extend it: "… 3530 1113 3330 0000 days ago, so it can't be that one" had read the last word as a seventeenth digit, which passed Luhn by chance, and the words between were removed with the number (seen in the blind run; no check had asked that the rest of the sentence survive).
   - **Across messages, a code at the seam is not part of the number** (`my card is 5555 5555 5555` then `CVV 737 4444`; `5555 5555 5555 737` then `4444`): the number is also looked for with one code-sized token dropped from the end of the earlier message or the start of the later one, and the code is masked with it. **A label ends at punctuation** (`ticket 1042, 4111 …`, `Booking 2291: 4242 …`), and an Amex or Diners grouping after a label is a card (`receipt 4821 3782 822463 10005`). The words inside a `[REDACTED …]` marker are never read as digits.
   - A number completed by a later message, in the same chat or in another of the customer's chats from the last 24 hours, is masked in that message **and** the earlier stored message is rewritten wherever it is stored: ADK's event rows, every LangGraph checkpoint and pending write of the thread (one copy per step), the model's echoes and reasoning, and the customer's episodes. The SQLite files are then compacted. The rest of a number whose last four was already given ("card ending 4444" … "the first twelve: 5555 5555 5555") is masked when it completes that last four into a card number, whether those digits come in one message or over two or three (round 6: `card ending 4444 zip 94107` / `5555 5555` / `5555`), as long as one message holds eight or more of them. **One exemption remains**, measured and listed below: pieces of at most five digits per message, one of which reads as a step-up answer ("… and my zip is 94107") and none of which says "card number", are taken for guessed last fours that pass Luhn by chance (the independent fuzzer's "typed in turn" family, 96 cases, which the rule protects).
   - In a message that carries card data (or just after one), every remaining bare 3-4 digit number is the security code and every month/year pair is the expiry. Elsewhere a code needs a cue phrase ("cvv", "security code", "code on the back") and an expiry "exp" or "expiry". "Verification", "security", "front" or "back" alone are not cues, and a last four or a ZIP is never masked, so "For verification: my last four are 6610" verifies.
   - **A code said twice is one code** (round 5, found by its first final pass: an unscripted customer pasted "security code: three eight six (386)", and the two renderings read as one six-digit run that was neither a code nor a card). A run that repeats one 3- or 4-digit value ("three eight six (386)", "3 8 6 = 386", "386 386") is that code; once a code is found, the same digits elsewhere in the message are masked too; a code dictated with commas ("three, eight, six") is one code. An expiry after its cue may be typed with a space or a dot ("exp 12 29"; "exp 12.29", which otherwise reads as an amount), or as a month name and two digits whatever separates them ("exp Dec 29", "expiry: July / 29", "exp Jul-29"); "January '27" is a month and a year, never a day; and a month and a year after a plain "expires" that has no subject of its own is the card's ("expires end of January '27" is masked, "my subscription expires July 2029" is kept).
   - **A code cue names the token after it** (round 6, the blind held-out run). In "CVC 047 1111" the code is 047, and what follows in the run is the rest of the number, marked as card digits in a card conversation: after an earlier card paste the first twelve digits of a number sent in two goes are masked at once, the message that completes it was then a seven-digit run no rule took, and the code was stored. **A month name and two digits directly before the card number are its expiry even with no cue**, as in a pasted card note ("September 27 4242 4242 4242 4242 / cvc 123"), unless a date word leads up to them ("charged on September 27 4242 …" is a day).
   - **A verification answer is not a security code.** Four bare digits beside a ZIP given after its cue ("Fine, it's 5127 and ZIP 60614"), in a message with no card number of its own, are a last four even right after a message that carried card data. Before round 5's second fix that answer was masked as a security code, and the customer had to type her last four alone. Three digits there, or four after a code cue, are still masked.
   - The model's replies get the card-number rule only, so case ids and amounts survive. Its stored reasoning gets every rule.
   - **What it does not catch**, measured or by construction, and why it is a backstop (A17):
     - a security code or expiry sent with **no card number** in the message or the two before it, when its cue is unusual or comes after the number: "813 is the code", "Amex code 6523", "front code: 1472", a bare "expires 05/31" or "expires 05 31" (without "card" or "it" before it, that reads as a date). These are 8 of the 9 misses in 900 cases of the independent fuzzer's seeds 41-43 on the final code. **That figure was reported as 10 misses in rounds 4 and 5 and was wrong:** the store scanner could not see a month name with an apostrophe year, so the fuzzer's phrasing "expires end of January '27", which the masker did not catch, was never counted. As the corrected scanner reads them, those seeds were 860/900 on the round-4 code (and the default seed 284/300, not 300/300); they are 891/900 and 300/300 now. A card number in the conversation makes every such number the code;
     - the other two of those misses: a **card number** spoken digit by digit where "one" is also a word ("…, the third is one one one one, last one one one one one", meaning "the last one: 1111"), which leaves 17 spoken digits that fail Luhn; and a code after an expiry written as "end of January '33";
     - **the exemption above, measured:** a 16-digit number typed as four messages of four digits with a ZIP phrase in one of them and no card cue is masked in 8 of 150 renderings (`fuzz-v2`, family "answer-sized pieces with a zip phrase"); removing the exemption would mask all 150 and unmask 22 of the 96 guessed-last-four cases in the independent fuzzer's two seeds. The number must be typed as answer-sized pieces for this to apply; a piece of eight or more digits is never exempt;
     - a 4-digit label joined **by spaces only** to a sixteen-digit number in fours ("order 1234 5555 5555 5555 4444"): twenty digits in fours after a label read as one reference, and it is masked in **0 of 150** renderings (`fuzz-v2`, family "a four-digit label joined by spaces to a number in fours"). The same label with a comma, colon or semicolon after it is 150/150, and with an Amex grouping after it the number is masked. Treating the last sixteen of twenty as a card would mask the tail of about one tracking or reference number in ten that is typed in fours, which is why it stays a miss;
     - an Amex security code typed as four bare digits beside a ZIP, right after a card message, with no cue ("1234 and ZIP 60614"): taken for a last four, the price of the verification-answer rule above;
     - a month name and two digits before a card number **after a date word** ("charged on September 27 4242 …") are kept as a date; if they were the card's expiry, it is stored. Without the date word they are masked (150/150 on `fuzz-v2`, family "a month name and a two-digit year directly before the number, no cue"; 12/150 before);
     - **found by the held-out corpus after the third pass, and not fixed in this round** (the corpus exists to measure what is left, and the provider balance did not cover another pass; 53/61, [every case](evidence/redaction/heldout-r6-blind.md)):
       - a role still takes a group when the number wraps over a line or a message, because "a complete card number wins over a role" is applied to tokens joined by separators on one line. After a phone cue: "my phone shows the card as 4242 4242 4242" + newline + "4242", "from my mobile app: 4111 1111 1111" / "1111", "reading it off my phone 6011 1111 1111" then "1117" as the next message, "call centre asked for 2223 0031 2200" / "3222" (0 of 4). At a message split: "Visa-4111 1111" then "1111 1111"; "4242 4242 4242" then "4242 days ago I activated this card"; "it's my Amex-3782" then "822463 10005" (1 of 4 masked). This is the round-5 review's blocker 2.4 again, one line break away from where I closed it;
       - an expiry joined to the number by a slash, "exp 09/27/4242 4242 4242 4242": the number is masked, "09/27" is kept (2 of 3 masked in that family);
     - by construction: a number spread over more than the last three messages, or over chats more than 24 hours apart; digits written as letters ("5S55"), encoded or reversed; amounts spoken with "hundred" or "thousand".
   - **What it over-masks:** a 13-19 digit number written in card groups with a card prefix, even if it is an order number (a mistyped card looks the same); a month name and two digits directly before a card number, with no date word before them, even when they were a day; in a message that carries card data, or right after one, any bare 3-4 digit number that is not a last four, a ZIP, an amount, a date or a year. Measured in [evidence/redaction](evidence/redaction/).
   - The agent sees `[REDACTED …]` tokens. When it sees one it may say that part was removed; when it sees digits it says they are kept in the transcript. It never says anything the customer said is "not stored" (procedure rule 10), and never coaches a way around the mask.
2. **Semantic writes** are a closed schema with a value grammar, timestamped, overwritten by key, and gated. The gate is **tiered**:
   - **Filing a dispute** needs the card's last four and billing ZIP (something the customer knows), typed in this conversation in the last 15 minutes.
   - **Changing or removing the contact channel**, the account-takeover actions, also needs a **one-time code** (something the customer has). `send_verification_code` has the bank text or email a 6-digit code to the mobile number or address **the bank holds on the account** (`customers.otp_channel`, `customers.otp_destination`: seeded, changeable only out of band, never by a tool, never copied into memory). The follow-up channel the customer picks in chat is memory; the number the bank texts is not, because redirecting it is exactly what a takeover wants. Then `confirm_verification_code()` **pauses the turn** until the customer's next message: ADK's `require_confirmation` flow, LangGraph's `interrupt()` (the pending write survives in the checkpoint). The code is six digits that never start with zero (so it is the same six digits wherever it is handled as a number), is stored as a salted hash, lives 5 minutes, is single-use, dies after 3 wrong entries, a new one can be sent after 60 seconds, and at most 5 are sent to an account in 24 hours; every wrong code is a failed attempt on the account's shared 3-strike lock, only a correct code resets that count, and the third failure's result says the account is locked.
   - **The typed code never enters the session** (round 6; the round-5 review's blockers 2.1 and 2.2). There is one definition of a typed code (`world.code_spans`: six digits together, as two threes, three pairs, or one at a time, with a space, dash or dot between, or in number words) and one place it is applied, a door in `run_turn` that every customer message passes before the model reads it and before anything stores it (`world.take_code_entry`):
     - while the bank holds an open code for the customer, **every** code-shaped span in what they type, in any of their chats, is replaced by `[REDACTED ONE-TIME CODE]`, whether or not it is the code. Nothing a customer can read tells the code from another six-digit number;
     - in the conversation the code was sent from, a message with exactly one span is the entry: the bank checks it once, counted like any attempt. A message with no span is not an entry ("Is it going to the number ending 0100? I'm in 94" is not a guess). A message with two or more is not compared at all;
     - what the shape rule leaves is searched once more, by salted hash, for the customer's own codes in any other rendering (`481,975`, `4819 75`): such a rendering is not an entry and is not kept. It is removed, and if it is the open code, that code is cancelled before anything is said, because it has been written into a conversation. A hash match is therefore never an answer about a code that can still be used;
     - a code that has run out is closed at the door when the message is not an entry for it, and the tool result says it expired and that no code is open. Before, the result for "it must have run out by now, please send me a new code" said the code "stays valid … without sending a new one"; in one run of round 6's second final pass LangGraph then sent nothing and told the customer "A fresh code went out just now";
     - `confirm_verification_code` takes no arguments and returns what the bank made of the entry. The model never receives a code, so it cannot repeat one or pass one to a tool.
     Round 5 did it the other way round: the model received the typed code, and a pass at the end of the turn replaced any six-digit run that hash-matched an issued code, in the store and in the reply. That made the marker a yes/no answer to "is this number the code", outside the attempt counter: the reviewer pasted 300 candidates in a second chat, read which line came back as the marker, typed it in the first chat and changed the contact channel with no failed attempt on record. It also had two definitions of a typed code (the bank stripped every non-digit; the redaction looked for six contiguous digits), so "481 975" was accepted and kept. What is left of the end-of-turn pass is defence in depth for text the model itself wrote, strings and numbers: the same search (`world.codes_exposed_in`: six digits in order with up to two other characters between them, dates and ids aside, by salted hash against this customer's codes only), and the same consequence, the open code cancelled and the text rewritten. Its first version in this round looked only for the forms the door takes and for six-digit numbers, and this round's own stored-code search caught it: a code that began with a zero, carried by a forced model response as the number 39074, stayed in LangGraph's checkpoint (`g73`, in a tuning pass). That is why no code starts with a zero now, and why the search is as wide as the check's.
   - The sent message is a row in the outbox with the full destination, the way an SMS gateway log has it. What the customer's phone would show is printed by the chat CLI after the turn, marked as the phone's, and `phone.py` tails the outbox for a two-terminal demo. What the step-up stops: the remote attacker who knows last four and ZIP, and the attacker who got in from pointing the bank somewhere else. What it does not stop, stated plainly: someone holding the customer's unlocked phone passes it, as at any issuer. What it costs: while a code can still be entered (five minutes from the send at most), any six-digit number the customer types in any chat is removed, an order number included. After that six digits are six digits again, except the customer's own dead codes.
   - **Each claim of this step, the check that would fail if it were false, and that check failing once.** A check that has never failed is a hypothesis; the round-5 review found three of mine that could not fail. For each claim below a *mutant* (`probes/mutants/mutants.py`, test code) puts the defect back, the named probe is run once per framework on the final code, and the run is kept in [evidence/mutants](evidence/mutants/). Seven of the eight fail their probe in both frameworks; the eighth fails in ADK and is caught by the second layer in LangGraph, as its row says:

     The stored-code search itself is held to its claim offline (`offline_checks.py`: it must find "481 975", "ok it says 447-526" and a code stored as a number, and must not take a clock time for a code), and so is the store scanner (a secret that ends a msgpack string; a number stored as a number).
3. **Reflection is incremental.** A session records how many turns are already reflected, so nothing is reflected twice. A turn leaving the 8-turn window is reflected mid-session, so it stays recallable. Each reflection is validated before storage:
   - card numbers are masked again;
   - other customers' names, case and transaction ids, last fours and ZIPs are scrubbed, and so are this customer's own last four and ZIP (a recalled episode must never be a way to verify);
   - unverified claims are labelled;
   - the outcome comes from the case system, not the model.

   Episode ids are unique (`E-<session>-<n>-<random>`) and stores insert, never replace, so a session id reused after retention deleted the session cannot overwrite an older episode (`g24`).
4. **Forgetting.**
   - **Retention without maintenance.** A transcript lives 30 days from its session's **first** turn. A turn on an older session first reflects what is unreflected, then deletes it, so the conversation continues as a new one whether or not maintenance has run (`g23`). An episode past its 180 days is never recalled, even before maintenance deletes it (`g38`). Maintenance also deletes expired travel notices of customers who never come back (`g37`). Deleted rows are compacted out of SQLite's free pages and WAL. LangGraph's store keeps an item's embedding after `delete`, so the agent deletes the vector row too (`no_orphan_vectors`).
   - **Erasure is a memory generation** (`cardcare/privacy.py`). Every session is registered with the generation it started in. `request_memory_erasure` raises the customer's generation under a write lock, then at once deletes facts, episodes, every other transcript, and every reminder that could still fire, `running` included, with every reminder note. Every memory write (a fact, an episode, a reminder) is made inside a guard that holds the same lock and lets it through only from a session of the current generation. Every session registered before the request keeps its registration at the old generation, so the chat the customer asked in, and a second tab that was open at the time, can store nothing more, whatever runs concurrently (`g58`; round 4 deleted the other sessions' registrations with their transcripts, and the other tab registered itself as current at its next turn: the round-4 review's finding 2.2a). The requesting chat's own transcript is deleted when the conversation ends, at the customer's next turn in another chat, when the background job finds it idle (30 minutes without a turn: a closed tab), or when a scheduled follow-up of that customer falls due (the scheduler finishes that customer's erasure before it fires anything of theirs), whichever comes first; a customer who asks to be erased and keeps typing keeps their open conversation until then, and the tool's result tells the model that what was typed in it can still be referred to (in one tuning run LangGraph, asked what the customer had said before the request, answered that it "was never stored at all"). **Round 5 said this and it was false under the command this README tells you to run:** the idle gate was in `run_maintenance`, but `tick` also runs the scheduler, whose `fire_followups` finished every pending erasure with no gate, so `tick --loop 60` still deleted an open chat a minute after the request; and the probe named for it, `g59-erase-open-tab-under-tick`, ran `run_maintenance` only (the round-5 review's 2.3). Now `finish_erasures_before_firing` is gated the same way, `tick` prints the customers it erased and the transcripts it deleted (it printed empty lists while deleting one), and `g59` runs the shipped `tick` in its own process; a second probe (`g79`) covers the follow-up-due case. A stale tab whose transcript maintenance has closed and that types again starts a new conversation under the old id, as after retention.
   - **Scheduled work cannot recreate memory.** A follow-up record carries the generation it was written in. A reminder from before an erasure was cancelled with it. A case follow-up, which must still reach the customer, runs in an in-memory session that stores nothing. `tick` runs maintenance before it fires anything, and finishes the erasure of any customer who has a record due (`g20`, `g21`, `g79`).
   - **A reminder's note lives only while the reminder can fire.** It is purged in the same statement that makes the record done, failed or cancelled (`g33`).
   - **What erasure keeps:** bank records (cases, the ledger, messages already sent, whose bodies may repeat a reminder's note) and, in `privacy.db`, only ids and timestamps: who asked, in which session, when, and each session's generation.

### What each framework made easy or awkward

- **Scope is a key prefix in ADK and a namespace convention in LangGraph.** ADK sessions are keyed by `(app, user, session)` and `user:` state is joined in automatically. LangGraph checkpointer threads have no owner, so per-user isolation of threads and of store namespaces is the harness's job (`thread_config`, `("facts", user)`).
- **`temp:` has no LangGraph equivalent in state.** Every state channel is checkpointed, so the per-invocation clock and session id ride in `context` instead. Both suites check that no clock value is ever persisted.
- **App-wide state is event-sourced in ADK.** `app:` keys can only change through an event, so ops seeds them with `EventActions.state_delta` (`seed_app_settings`). Writes from outside a turn (erasure, maintenance) go through an event on a throwaway session. In LangGraph these are `store.put(("app",), ...)` and `update_state`.
- **ADK applies a tool's state change after the tool returns**, when it appends the tool's event. A fence checked inside the tool can therefore be overtaken by an erasure from another chat before the write lands. The ADK agent re-checks the session's generation when the turn ends and deletes a fact the turn wrote if an erasure got in between. LangGraph's store write happens inside the tool, inside the guard.
- **ADK's built-in local memory service did not fit the write path.** ADK 2.13 ships `SqliteMemoryService`, but it indexes raw session events with keyword search and has no `delete_memory`. So the ADK agent implements `BaseMemoryService` itself. Measured, embeddings beat keyword search clearly ([evidence/retrieval](evidence/retrieval/results.md)): recall@1 0.80 against 0.47 on the policy KB, and 0.92 against 0.67 on an episode history.
- **LangGraph's store forgets the item but not its vector.** `SqliteStore.delete` leaves the embedding in `store_vectors`; erasure and retention delete it explicitly.
- **Rewriting stored history** is a SQL update of JSON rows in ADK (`events.event_data`). LangGraph keeps a serialised copy of the whole message list per step, so a rewrite goes through the saver's serializer for every checkpoint and pending write of the thread. **The messages are not the only copy of what a model said.** Once each tool call is its own task, the `Send` packet that dispatches it holds the call, arguments included, in the `__pregel_tasks` channel of the checkpoint and of the pending writes. Round 5's first redaction rewrote the messages, the resume values and the interrupts and left the packets, so a one-time code the model passed as an argument stayed in the store behind a transcript that showed it redacted; the rewrite now maps over a `Send`'s argument and the packets' writes too (`_map_strings`, `scrub_earlier_messages`). In ADK the function call's arguments live once, in the event row. The general lesson is to enumerate a framework's copies from its storage, not from the object the application holds.
- **The agent is built per turn, not once.** A session's tool set is a security property that depends on its kind: a live chat, or a scheduler follow-up bound to its record. An ADK `Runner` is tied to one root agent, so `run_turn` builds the agent and `Runner` for the turn's kind, and LangGraph compiles the graph per turn. Measured without the model, this costs:
  - ADK: **0.02 ms** per turn, sharing the session and memory services; litellm reuses its HTTP client across turns (one client-cache entry for three calls);
  - LangGraph: about **70 ms** per turn (41 ms to compile, plus a second `build_tools`), and a new `ChatDeepSeek` client each turn, so no keep-alive across turns (about 35 ms per call, within noise).

  That is about 1-3% of a multi-call turn in LangGraph. Caching the live-chat agent, `Runner` or graph per `(kind, disabled_tools)`, and one model client per harness, would be the leaner design; follow-ups would still be built per record.
- **Bounding working memory** is a `before_model_callback` that rewrites `llm_request.contents` in ADK, and a slice of `state["messages"]` in the LangGraph agent node. Both cut at a customer turn, so tool-call pairs stay whole.
- **Parallel tool calls are a different execution model.**
  - ADK 2.13 runs sync tools one at a time, and `tool_context.state` writes through, so `remember_customer_fact` sees a `verify_identity` from the same model response.
  - LangGraph runs the calls of one model response concurrently. Here each call is its own task (a `Send` to the `ToolNode`, see the next bullet but one), every task reads the state from before the response, and `Command` updates merge afterwards through reducers.
  - So nothing that must hold under concurrency is a read in one statement and a write in the next. A verification attempt, a dispute (behind a one-open-case-per-transaction index) and an erasure are each one `BEGIN IMMEDIATE` transaction. Evidence is appended by one `UPDATE`. One message per follow-up and one reminder per local day are unique indexes. `identity_verified_at` has a reducer. The forced probes `g17`, `g25`, `g26` and `g27` drive both frameworks with parallel calls in one model response; before round 4, LangGraph opened duplicate cases, lost evidence notes and evaluated six guesses past the lock.
- **A malformed tool call fails differently.** DeepSeek sometimes emits a call whose JSON arguments do not parse.
  - ADK ends the turn on `MALFORMED_FUNCTION_CALL`. The customer gets no reply and the dispute is silently not filed.
  - LangGraph puts the call in `invalid_tool_calls`, which ToolNode never runs, and every later request is an HTTP 400.
  - Both agents answer it like any failing tool: it becomes a call to `report_malformed_tool_call` under the same id, and that tool returns the parse error, so the model makes the call again (`g19`).
- **A turn that waits for the customer is a different primitive in each framework.** ADK's `FunctionTool(require_confirmation=True)` does not run the function on the first call: it emits an `adk_request_confirmation` call, ends the invocation, and runs the function when a `FunctionResponse` to that call arrives, with the response's payload readable in the tool (`tool_context.tool_confirmation.payload`). ADK's `LongRunningFunctionTool` pauses only when the function returns `None`, and then the result the model sees is whatever the harness later sends, so it suits work that completes elsewhere (the reviewer's held draft), not an input request. LangGraph's `interrupt()` inside a tool raises out of the `ToolNode`, is persisted as a pending write, and resumes with `Command(resume=...)`, **re-running the interrupted task from the top**, so nothing with a side effect may precede it (the code is sent by a separate tool). "The task" is the catch: with the usual wiring, one `ToolNode` step for all the calls of a model response, a `send_verification_code` in the same response as the wait was run again on resume, the bank issued a second code (a resend is allowed after a minute), and the code the customer had correctly typed was refused and counted as a failed attempt. The graph therefore dispatches every tool call as its own task (`Send`), so only the paused call re-runs and the calls beside it keep their recorded results (`g64`, which fails on the single-step wiring: two codes, one failure row). In both, a plain message while a wait is pending must be routed as the answer, or ADK's LiteLlm synthesises a placeholder tool result and LangGraph answers nothing; `run_turn` checks for a pending wait before building the turn.
- **A tool result lost to a crash is repaired the same way in both, and every write tool is safe to repeat.** A process that dies after a tool's database effect and before the framework records the result leaves a dangling call (ADK: a function call with no function response in the events; LangGraph: an AI message whose tool call has no tool message), and the next turn would fail on it. Round 4 answered such a call with "this call was interrupted and did not run", which is a guess. Round 5 answers "the result of this call was lost … safe to call again … or check the current state first", and makes it true: a repeated filing returns the open case and schedules the follow-up the crash skipped (two databases, so the two steps are not one transaction); a note attached again is attached once; after the repair has told a conversation that a result was lost (it records when: `lost_result_at`), the same wrong guess, or the same code, made again by that conversation within two minutes is the same attempt, not a new one (`verification_attempts.session_id`, `guess_hash`, `verification_challenges.consumed_in`), while with no lost result every entry counts, so a customer who types the same wrong code twice has made two attempts (`g47`); the possession proof is rebuilt from the bank record at the next turn (`world.possession_proved_at`: the code this conversation consumed within the last 15 minutes), and a confirmation interrupted after the bank recorded the code as entered correctly is completed from that record, by whichever route the framework leaves open. In LangGraph the call is dangling and the repair answers it. In ADK a call that paused is not dangling (ADK recorded its own "requires confirmation" placeholder for it) and its wait is no longer unanswered (the `Runner` stores the customer's entry before it re-runs the tool), so the harness treats a confirmation as open until the tool's result follows the answer, which is how ADK's own request processor decides a confirmation is consumed; the customer's next message resumes the tool, and the tool returns the recorded proof (`g63`, where the pause is forced so the path does not depend on how the model chose to take the code). A reminder is one per local day, a message one per follow-up, a fact a key overwrite, an erasure a generation that can only go up. The repair leaves a one-time-code confirmation that is still waiting for the customer alone. A turn that fails still redacts any one-time code it leaves in the stored conversation. In LangGraph every session channel has a last-value reducer, because a thread resumed after a crash mid-turn still holds that turn's pending writes. Live: `g61-lost-tool-result` kills the chat process after `attempt_verification`, `open_case`, `add_case_evidence` and `attempt_code` (`probes/crash/sitecustomize.py`, test code) and resumes the conversation in both frameworks.
- **A deleted session continues differently.** The ADK `Runner` runs with `auto_create_session=True`, so a chat whose transcript an erasure deleted gets a fresh, empty session under the same id at its next turn, with no error (round 4's README said it breaks with `SessionNotFoundError`; the round-4 review showed it does not). LangGraph silently recreates a deleted thread from the running graph's state. In both, the registration row outlives the transcript, so the recreated session is stale: it stores nothing and is deleted again when idle, never reflected.

## Running it

```bash
cd modules/07-memory-state/code
python3.13 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
export DEEPSEEK_API_KEY=...        # or put it in a gitignored code/.env; module 01's .env is also read
```

There are two commands per agent, for two different jobs.

**`chat` is how you talk to the agent.** It is the only command a person who wants to chat needs. Conversations, facts and episodes persist under `var/<framework>/interactive/` from one chat to the next:

When the agent sends a one-time code (a contact-channel change), the chat prints what the customer's phone shows, marked `[your phone, sms to +1 415 555 0100]: Your Kestrel verification code is …`, and you type the code back. The agent never sees that line.

**`tick` is the system's clock and janitor, not a way to talk to the agent.** It takes no input. One pass first runs memory maintenance:
- finishing erasures;
- deleting expired facts, episodes and transcripts;
- closing idle chats into episodes.

Then it fires every follow-up and reminder that is due, each into a fresh scheduler session. No customer is in that session, and it can only read and send its one message.

In production a cron job or a background worker runs it. Locally nothing runs it for you, and nothing in chat mode advances the clock. So run it yourself only when you want to see time-driven memory happen: a dispute's follow-up, a reminder you asked for, retention, or a closed-tab erasure completing. The suites call the same functions at the instants their steps name.


## Evidence: what was run and what failed

**How it was validated.** No mocks and no unit tests. Every conversation below went to the real agent and the real model, from empty stores.
- Checks read only what a run produced: tool calls and results, replies, and every store's contents, raw file bytes included. Each check is tagged with the memory type it proves.
- Open-ended replies are scored by an LLM judge (A19) whose verdicts are recorded in the run's `steps.json`. Every check is a pure function of that record, so `--rescore` never re-runs anything. A claim about storage is paired with the store scan **per item**: the judge says which of card number, security code and expiry the agent claimed removed or not stored (its question now spells out that "pass" means "it made the claim"), the scanner says which are in the stores, and the claim is false only where the two meet (round 5: the round-4 review showed the earlier pairing failing an honest agent that said a redaction token's expiry was removed over a store that had leaked the number).
- **Card data in stores** is decided by `cardcare/store_audit.py`, which shares no code with the masker. It reads number words both ways and every published test number a probe uses, and it reads a store as a store: the raw bytes of every file (write-ahead logs included), with bytes that are not text as separators, and every string of every value of an SQLite file, msgpack decoded. Round 5 added the second reading after finding that the first alone was blind on LangGraph: in a msgpack checkpoint a string runs straight into the next value's header byte, so a secret that began or ended a stored string had no boundary and matched nothing. Re-scanning the 296 store directories of round 5's first final pass with the corrected reader found no card data the old one had missed, and a one-time code in 11 LangGraph stores, which was a product defect ([failures.md](evidence/failures.md)).
- **Forced probes.** Some probes force a model response instead of asking for one: parallel calls (`g17`, `g25`-`g27`), a corrupted tool call (`g19`), a fact carrying instructions (`g35`), digits the customer never typed (`g40`), a masked message (`g41`). Everything after the forced response is the real framework.
- **The final pass was declared final before it started.** Its code hash was recorded before it and checked unchanged after it, and the record is committed: [evidence/final-pass-code.sha256](evidence/final-pass-code.sha256), recomputable with `python code_hash.py` on the commit it names (round 4 kept the hash outside the repository, which the round-4 review rightly called a missing artifact). Round 4 had two such passes: the first ran its blind held-out set, which found defects and reopened it (A24). Round 5 had three: the first (on `8051dbd`, scores in [evidence/history/review-r5-final-1](evidence/history/review-r5-final-1/)) was reopened by a security code its own unscripted customer got past the masker; the second (on `5140524`, [review-r5-final-2](evidence/history/review-r5-final-2/)) held every store and guarantee and was reopened for one agent failure that recurred in both LangGraph runs; the tables below are the third. From the third on, a pass is reopened only by a product defect, and a single-run wording or recall miss is quoted and kept. **Round 6 had three.** The first (on `3bf1a29`, [scores](evidence/history/review-r6-final-1/)) passed every suite I had written and was reopened by the blind held-out run.
