# Source audit — literature grounding of the conceptual content

**Scope:** every conceptual claim in `modules/07-memory-state/README.md` is audited against research surveys, primary papers, and (where the claim is legal or infrastructural) standards and industry primary docs. **ADK-specific API and product content is excluded by design** — `Session`, `State`, the `user:`/`app:`/`temp:` *syntax*, `MemoryService` and its implementations, `load_memory`, `preload_memory`, `add_session_to_memory`, `add_events_to_memory`, `add_memory`, `MemoryEntry`, `output_key`, `EventActions`/`state_delta`, `{key}` templating, the "ADK at a glance" callouts, and the "In DSH" note are documented elsewhere and are not audited here. What *is* audited are the concepts ADK merely illustrates — e.g. "memory should be partitioned by scope so one user's data cannot reach another" is in scope even though the prefix syntax is not. Every conceptual claim appears exactly once; the README's own section names are given in parentheses so the mapping is unambiguous. Citations marked *(2026)* post-date most of the module's assumed knowledge cutoff and are flagged as such.

## How to read this

**Justified** — a survey or primary paper states the claim, or establishes it directly. **Partially justified** — the direction is supported, but the specific formulation, strength, or taxonomy is the module's own extrapolation; the entry says exactly which part is supported and which is not. **Unjustified / novel** — no literature was located; the claim is the module's own engineering framing, an analogy, or a normative stance. Where the literature *conflicts* with the claim, the entry says what the literature actually says instead. A finding of "this is the author's own construction" is a successful audit result, not a failure — and several of the module's most load-bearing claims are exactly that.

## Justified

- **#17 — Contradiction: two memories disagree, and the fixes are overwrite/consolidation, conflict detection, escalation** *(The four failure modes: staleness, contradiction, leakage, recall).* This is the best-grounded claim in the module. **Zep** implements exactly what the module prescribes: an LLM compares new graph edges against semantically related existing edges to identify potential contradictions, and when it finds temporally overlapping contradictions it invalidates the affected edges by setting their `t_invalid` to the `t_valid` of the invalidating edge, consistently prioritising new information [24]. **Mem0**'s LLM-driven update step exposes a `DELETE` operation defined as "removal of memories contradicted by new information" [23]. The knowledge-conflict literature names context–memory and intra-memory conflict as first-class phenomena and surveys both behaviours and solutions [26]. **Du 2026** independently recommends contradiction detection with flagging-for-resolution plus periodic consolidation [20]. All four elements of the module's cell — the definition, the failure signature ("the answer flips depending on which memory was retrieved"), the merge/overwrite fix, and escalation — are supported.

## Partially justified
- **#1 — Memory failures split into continuity failures and isolation failures, and neither is "the model hallucinating"** *(Opening scene; Failure mode callout).* Supported direction: **MAST** finds a 41%–86.7% failure rate across seven state-of-the-art multi-agent systems and concludes that failure "is not merely a function of challenges in the underlying model," with explicit memory-adjacent modes (*loss of conversation history* 2.80%, *conversation reset* 2.20%) sitting inside a **system-design** category whose failures "reflect flaws in pre-execution design choices regarding system architecture, prompt instructions, or state management" [30]. **Du 2026** frames staleness/contradiction/deletion-compliance as engineering realities rather than model properties [20]. *Not* supported: the specific *two-family* partition. MAST is not a memory taxonomy and disclaims exhaustiveness; it has no memory category and no continuity/isolation split. The dichotomy is the module's own organising device.

- **#2 — Memory is not "remember more"; it is "remember the right thing, at the right scope"** *(Opening scene).* The direction is well supported (retrieval filtering, precision, and selective forgetting are recurring concerns across [20], [13], [22]). The *formulation* is not from the literature: it originates in the practitioner post the module already cites [36], which states the same thesis as "More memory is not a better agent. A better agent forgets on purpose." No surveyed paper states the claim in this form.

- **#3 — Treating memory as a feature to bolt on rather than a correctness problem is the root failure** *(Failure mode callout).* **Du 2026** treats memory as a full engineering discipline with a write path, risk analysis mapping memory failure modes to downstream consequences, and evaluation metrics that jointly assess memory quality and decision quality [20]; **MAST**'s "primacy of system design" supports the general shape [30]. *Not* supported: "correctness problem" as a category, and "root failure" as a causal ranking. No source located that frames memory design as a *correctness* problem or ranks this as *the* root cause. This is a normative stance — a defensible one, but the module's own.

- **#4 — The kind-taxonomy: working/short-term, semantic (facts), episodic (events), procedural (how-to), and its mapping to cognitive science** *(The memory taxonomy).* The four-way labels are genuinely established. **CoALA** organises language agents into "short-term working memory and several long-term memories: episodic, semantic, and procedural" [6]. The underlying psychology is real: semantic vs. episodic is Tulving's distinction [7] ([8] is his retrospective summary), procedural memory is a subtype of nondeclarative/implicit long-term memory in Squire's taxonomy [11] ([10] for the declarative/nondeclarative synthesis; [9] is the foundational synthesis placing skills and habits under nondeclarative memory), and a capacity-limited working memory is Baddeley & Hitch's [12]. **Du et al. 2025** independently confirms the labels as a live organising scheme [13]. *Not* supported: that any of these sources organises them as "seven types, two axes, four scopes." The seven-type list, the two-axes cut, and the four-scope layer are the module's (via [36]) synthesis. Also note the sources disagree with each other about what belongs where — see #7. Two refinements the module should carry: **CoALA's actual lineage is Atkinson & Shiffrin (1968) and Baddeley & Hitch (1974) via the Soar cognitive architecture** — not Tulving and Squire directly, so citing CoALA as a *cognitive-science* warrant for the four-way split overstates it; and the survey that *does* make the cognitive-science mapping explicit uses **five** categories (it adds sensory memory) and cites Tulving, Baddeley, Atkinson & Shiffrin, and Squire for them [54]. So the four-way version is a defensible subset, not the literature's full taxonomy.

- **#6a — Working memory fails by *overflow*; long-term memory fails by staleness/contradiction/leakage/failed recall; design them separately** *(The memory taxonomy, observation 1).* The overflow half is empirically supported, though not in the module's terms: **NoLiMa** shows length-dependent collapse beyond literal matching — at 32K, 11 models drop below 50% of their strong short-length baselines, and GPT-4o falls from 99.3% to 69.7% [45]; **RULER** finds that although models claim 32K+ context, only half maintain satisfactory performance at 32K [46]. *Not* supported: the word "overflow," which is the module's interpretive label (the benchmark finding is *attention/retrieval degradation as context grows*, not a memory-management harness failing), and the claim that these are "different diseases" established in the literature. A further precision note if the module ever leans on *cognitive* working memory to justify this: human working-memory capacity is **not** a single fixed number — **Miller's** famed seven-plus-or-minus-two was "meant more as a rough estimate and a rhetorical device than as a real capacity limit," and **Cowan's** estimate of roughly four chunks holds only under stated boundary conditions (rehearsal and chunking blocked) [56], [57]. Capacity is material- and strategy-dependent, so "fails by overflow" is an engineering metaphor for hard context truncation, which has no human counterpart. The long-term list is a preview of the module's own taxonomy (see #26).

- **#6b — The long-term failure list itself** *(The memory taxonomy, observation 1; The four failure modes).* **LongMemEval** measures five long-term memory abilities including **"knowledge updates"** and **"abstention"** [25], which map onto staleness/contradiction and recall failure respectively; **Du 2026** has a section titled "Staleness, contradictions, and drift" and separately treats access-scope violations and privacy leakage [20]. *Not* supported: the specific four-way grouping and its order — see #26.

- **#8 — "Stored is not the same as active": a database holds the conversation, but the model cannot use a byte of it until it is back in the prompt** *(The memory taxonomy, observation 3).* Mechanically correct and directly supported. **CoALA** states the premise: "Language models are stateless: they do not persist information across calls," and on each LLM call "the LLM input is synthesized from a subset of working memory" [6]. **MemGPT** builds its entire contribution on it, describing virtual context management as moving data between fast and slow memory tiers so the model sees only what is currently resident [12]. The module's worked illustration — the "it remembered!" illusion is really the constraint still being re-sent each turn — is a correct application of this. *Extrapolated:* the framing "storage is potential, working memory is what the model can actually use" is the module's (and [36]'s) phrasing, not a quoted result; and the module treats it as a *discovery*, whereas it is a documented property of stateless inference.

- **#9 — Parametric memory: frozen at training time, cannot hold anything private, cannot be surgically corrected, is confidently wrong, and fine-tuning is a poor way to store facts that change** *(The memory taxonomy — "Parametric memory is a floor, not a feature").* Four of five sub-claims are supported, but "surgical correction" needs a more precise citation than ROME alone. **Frozen / long tail:** Mallen et al. find LMs struggle with less popular factual knowledge and that scaling fails to appreciably improve long-tail memorisation [31]. **Cannot be surgically corrected:** the right sources are the *negative* results, not the editing mechanism. **Cohen et al.** show that injecting one fact "introduces a 'ripple effect'": current methods "fail to introduce consistent changes in the model's knowledge," and a simple in-context editing baseline outperform them [47]. **Yao et al.** find model editing is "somewhat limited" on portability, locality, and efficiency — ROME "performs well up to n=10, then degrades at n=100," and ROME/MEMIT perform well on GPT-NEOX-20B but fail on OPT-13B [48]. ROME itself should be cited only for what it does: a rank-one weight update localising a factual association, with the authors' own limit that "it only edits a single fact at a time, and it is not intended as a practical method for large-scale model training" [33]. **Fine-tuning is a poor way to store facts:** Ovadia et al. find that although unsupervised fine-tuning offers some improvement, RAG consistently outperforms it for both existing and entirely new knowledge, and that LLMs "struggle to learn new factual information through unsupervised fine-tuning" [34]. *Caution:* [34] tests *unsupervised* fine-tuning on injected corpora, not instruction tuning, and measures knowledge *injection* rather than facts that *change* — the module's stronger phrasing ("a poor way to store facts that change") outruns the paper. *Not* directly supported: "**confidently** wrong" — the module supplies no calibration citation, and the claim needs the hallucination-calibration literature specifically, not knowledge editing. Also *extrapolated:* "cannot know anything private" is an information-flow consequence of training-time freezing rather than a measured result, and the module's framing of parametric memory as "a floor, not a feature" is normative.

- **#11 — Scope partitioning is *the* memory design decision, and it is the boundary determining whether one user can see another's data** *(Working memory: Session & State — scoping prefixes).* The substantive claim is supported: **Collaborative Memory** builds multi-user, multi-agent memory with asymmetric, time-evolving access controls, private vs. shared tiers, immutable provenance on each fragment, granular read policies that "project existing memory fragments into filtered transformed views," and write policies determining retention and sharing [27]. **Du 2026** lists per-user access scoping, automated PII redaction, and access-scope-violation metrics as deployment requirements [20]. *Not* supported: the superlative — that scope is "*the*" memory design decision. Nothing located ranks scoping above, say, the write path or retrieval quality; the literature treats it as one load-bearing dimension among several. The ADK docs the module draws on describe prefixes as an *organising* mechanism, not a security boundary — which is worth noting, because the module's leakage claim needs a security boundary and the cited API docs do not claim to provide one.

- **#12 — The retrieval design tradeoff: preload every turn vs. load on demand** *(Long-term memory: the MemoryService).* The direction is supported. **Mallen et al.** show that unassisted LMs remain competitive on high-popularity entities while retrieval-augmented models dominate elsewhere, and derive an adaptive method that "retrieves non-parametric memories only when necessary," improving performance [31]. **Self-RAG** [43] criticises retrieving "regardless of whether retrieval is necessary" and learns on-demand retrieval [43]. **MemGPT** is the canonical architecture for deciding what to page into the window versus what stays in the slow tier [12]. *Not* supported: the framing as a *memory-tier* tradeoff. These sources gate *per-query retrieval* for accuracy and efficiency; they do not study a preload-versus-on-demand *memory* policy, and the "only works if the agent knows to ask" failure mode for load-on-demand is the module's own formulation. *Note:* the module's preamble to this table ("Three implementations, three tradeoffs") is ADK product content and is out of scope.

- **#13 — Consolidation merges contradictory memories into one coherent memory rather than appending them** *(Long-term memory: the MemoryService).* Supported: **Mem0** dynamically extracts, **consolidates**, and retrieves salient information, and its `UPDATE`/`DELETE` operations reconcile new facts against existing similar memories rather than blindly appending [23]; **Du et al. 2025** names Consolidation as a core memory operation, defined as "transforming short-term experiences into persistent memory" [13]; **Zep**'s edge invalidation is the same idea realised on a temporal graph [24]. *Unjustified within this claim:* the assertion that consolidation "is the direct answer to the contradiction failure mode." Mem0 and Zep reconcile at write time; the module additionally asks consolidation to *fix* contradictions already present, and the module's own caveat about fidelity loss implies it does not. *Novel:* the analogy "the long-term analog of M4's compaction — both are lossy reconciliation of history." No source located draws a compaction↔consolidation equivalence; [13] in fact explicitly distinguishes compression from consolidation (compression reduces memory at inference; consolidation moves short-term to persistent). This is the module's own analogy.

- **#14 — Episodic memory stores distilled reflections/lessons, not raw transcripts; the summary is what gets reused** *(The loop: episodes become procedures).* Supported: **Generative Agents** stores a complete record of experience and "synthesize[s] those memories over time into higher-level reflections," which are then fed back into the memory stream and retrieved for planning [19]; **Reflective Memory Management** summarises interactions across utterances, turns, and sessions into a personalised memory bank for future retrieval [21]; **Reflexion** stores the self-reflection model's verbal outputs rather than raw trajectories [29]. *Extrapolated:* "the full transcript is for humans and traces; the lesson is what gets retrieved" is a strong split — Generative Agents retains the raw memory stream *and* the reflections, and both are retrievable. The module's clean discard-the-transcript posture is its own design choice.

- **#15 — Episodic → procedural promotion; both extremes fail; promotion needs a threshold, reviewer, and retraction path** *(The loop: episodes become procedures).* Supported: **Reflexion** improves across trials by storing verbal self-reflections and reusing them, with no weight updates [29]; **Voyager** maintains "an ever-growing skill library of executable code," adding verified programs as retrievable, composable skills and explicitly "bypass[ing] the need for model parameter fine-tuning" [35]; **ExpeL** autonomously gathers experiences, extracts natural-language insights, and recalls them at inference "without requiring parametric updates" [28]. **CoALA** ranks the risk exactly as the module does — writing to procedural memory "is significantly riskier than writing to episodic or semantic memory, as it can easily introduce bugs or allow an agent to subvert its designers' intentions" [6]. *Not* supported: the specific policy apparatus. No source located prescribes a numeric *threshold*, a named *reviewer*, or — critically — a **retraction path**. Voyager has no mechanism for removing or demoting a stored skill, and the retract-a-promoted-rule operation is essentially unsupported in the literature; the closest work is recent (2026) and preprint-stage [20]. The "both extremes are failures" table is the module's synthesis. (Also note a precision issue if this is ever cited: Reflexion's buffer is *bounded* — a rolling window of Ω=1–3 stored experiences, persisting across trials *of the same task*, not durable cross-task memory [29].)

- **#16 — Staleness: a stored fact is no longer true; fixes are timestamps, TTL/expiry, and re-verification before use** *(The four failure modes).* Supported: **Zep** is bi-temporal, tracking `valid_at`/`invalid_at` on the event timeline and `t'_created`/`t'_expired` on the transactional timeline, with a section titled "Temporal Extraction and Edge Invalidation" [24]. **Du 2026** recommends temporal versioning (prefer the newest record), source attribution (user statement over agent inference), and periodic consolidation, and observes that without explicit mechanisms "the agent has no way to distinguish the 2024 address from the 2022 one" [20]. **LongMemEval** measures knowledge updates and temporal reasoning as core abilities [25]. *Not* supported: TTL/expiry as a researched memory mechanism — expiry appears in the surveys as a recommendation ("periodic expiration") rather than a studied technique, and the *re-verify before use on consequential facts* step is the module's own policy prescription with no located source.

- **#18 — Leakage: data crosses a scope boundary; fixes are scope prefixes and scope-filtered retrieval** *(The four failure modes).* Supported: **Collaborative Memory** enforces current user–agent–resource constraints through granular read policies and projects memory into filtered transformed views, with provable adherence to time-varying policies and full auditability [27]; **Du 2026** requires per-user access scoping and treats access-scope violations as an evaluation metric [20] and notes the residual hole that when memories have leaked into fine-tuned weights, external deletion is insufficient and machine unlearning is the only path — "far from production-ready" [44]; **Authorization Before Context** [53] enforces an audience boundary at the memory-to-context transition, proving forbidden facts are absent *before* the model is called, though its evidence is self-described as preliminary and synthetic; **GDPR** supplies the legal half of "PII needs a scope boundary" — Art. 5(1)(e) storage limitation and Art. 17 erasure, with Art. 17(2) making downstream propagation of a deletion obligatory [37]. *Not* supported: "never store secrets" as a leakage fix (classified under #22 instead, since it is an exfiltration control, not a scoping control), and the implication that prefix-based key naming is a security boundary — the sources implement actual access-control policies over resources and principals, which a naming convention is not.

- **#19 — Recall failure: the right memory exists but the wrong one comes back; the fix is matching retrieval method to query type; and recall degrades as the store grows** *(The four failure modes; Worked example — "The failures, prevented").* Supported: that retrieval is the weak link and matching method to query matters — **LongMemEval** decomposes memory design into indexing, retrieval, and reading, and shows a ~30% accuracy drop for commercial assistants and long-context LLMs across sustained interactions [25]; **Generative Agents** combines relevance, recency, and importance into a single retrieval score and reports that "the most common errors arose when the agent failed to retrieve relevant memories" [19]; **Zep** adds time-bounded retrieval over valid date ranges [24]; **A-MEM** adds link-based organisation via Zettelkasten-style dynamic indexing and linking [22]. *Partially contradicted:* the module's implication that irrelevant material uniformly degrades recall. **The Power of Noise** finds the opposite for *random* documents — "adding random documents in the prompt improves the LLM accuracy by up to 35%" — while what actually harms accuracy is the retriever's **highest-scoring, semantically related but answer-free** documents (up to −67% in reported cases) [0]. Any "noise hurts retrieval" gloss is wrong; the defensible extraction is the *distractor* result. *Unsupported:* "recall degrades as you succeed — every fact you add dilutes the precision of the next retrieval." No primary source measuring an agent memory store's precision-versus-size curve was located. The nearest honest support is normative and adjacent: [20] asserts that a failure to discard outdated information "gradually poisons retrieval precision," names "capacity (performance degradation as the memory store grows)" as an evaluation dimension [20], and [13] lists scale among memory's open challenges — but these are survey assertions and metric proposals, not measurements, and the module's own cited survey [2] makes no such claim. **Treat the dilution claim as a design hypothesis, not a finding.**

- **#20 — "Memory is a source of truth and the model treats it as one": a stale memory is wrongness that presents itself as rightness** *(The four failure modes).* Partially supported and partly *contested* by the literature the module should be citing. Supported: knowledge conflict between context and parametric memory is a first-class, surveyed phenomenon, with categories for context–memory, inter-context, and intra-memory conflict [26]. Contested: the confident-overreliance picture is not the consensus. **Mallen et al.** find models are competitive from parameters on popular facts and that retrieval should be conditional rather than default [31]. **Xie et al.** find LLMs can be "highly receptive to external evidence even when that conflicts with their parametric memory, given that the external evidence is coherent and convincing," while also displaying a strong confirmation bias when the evidence partially agrees with parametric memory [32]. Context does not simply win, and memory is not simply trusted. *Not* supported: "the model has no reason to doubt its own memory" — a normative gloss on model psychology with no located source; and "memory is a source of truth" is a design stance the module adopts, not a finding. **Du 2026** does support the practical half: stale or hallucinated recall "can be worse than no recall at all" [20].

- **#22 — Memory is an exfiltration surface; three things must never be stored: secrets, unverified facts, PII without retention/consent/scope policy** *(What memory should never hold).* Supported in substance. Exfiltration via retrieved content is demonstrated: **Greshake et al.** show indirect prompt injection compromising real-world LLM-integrated applications by planting instructions in retrieved data, and document data-theft side channels via search queries and markdown links [38] — *but* the paper contains no markdown-*image* exfiltration proof-of-concept (it never uses "image request"); that specific primitive is documented by OWASP LLM01:2025 [53], and the memory-specific attack surface is established by **AgentPoison**, which backdoors memory/knowledge bases at under 0.1% poison rate with >80% attack success [39]. Secrets and PII in model-reachable text are extractable: **Carlini et al.** extract training data [40] and **Lukas et al.** analyse PII leakage in language models [41]. On PII policy, **GDPR** Art. 5(1)(e) (storage limitation), Art. 17 (erasure) and Art. 25 (data protection by design and by default) do ground retention, consent, and scope as legal requirements, and Art. 17(2) makes propagation of erasure to downstream copies obligatory [37] — which is precisely the hard case for derived memory (summaries, graph edges, promoted rules). Two precisions: the *consent basis* is Art. 6(1)(a) + Art. 7 (Art. 17 is the erasure *consequence* of withdrawal), and Art. 25(2) expressly names "the period of their storage and their accessibility," which is the strongest textual hook for retention controls. **A gap worth flagging:** no authoritative AI-specific PII-retention rule for agent memory was located — NIST AI 100-1 is explicit that the framework is "voluntary, rights-preserving, non-sector specific, and use-case agnostic" and prescribes no retention windows — so this module's retention policy rests on the general legal baseline plus the author's engineering judgement. *Extrapolated:* the specific three-item never-store list, and "unverified facts" as a distinct category, are the module's own policy; no source was located that frames the never-store rule this way. Also *over-claimed if read literally:* "anything in memory is reachable by the model, and a reachable secret is a leaked secret" is a risk statement, not a demonstrated equivalence.

- **#23 — The write path has four stages (extraction, validation, update, deletion); extraction is usually model-driven and imports the model's judgment; extraction output is a candidate, not a write** *(The write path — and forgetting on purpose).* Supported: **Mem0**'s pipeline consists of "two phases: extraction and update," where the model chooses among `ADD`, `UPDATE`, `DELETE`, and `NOOP` for each candidate fact [23]; **Du 2026** devotes a section to "The write path," specifying filtering to reject low-signal records, canonicalisation, deduplication, priority scoring, and metadata tagging (timestamp, source, confidence) to support downstream structured queries, and warns that "storing every interaction verbatim is tempting and almost always wrong" because noise "degrades retrieval precision" [20]; **Du et al. 2025** names Updating among six core operations, split into intrinsic and extrinsic (user-feedback-driven) updating [13]. *The four-stage framing is the module's:* Mem0's four items are mutually exclusive per-candidate operations, not a sequential pipeline, and the module's *validation* stage (verified this turn vs. the model's paraphrase) is not a named stage in any located source — [20]'s nearest equivalents are confidence metadata and source attribution. *Supported direction:* that model-driven extraction imports model judgment is the explicit design premise of both Mem0 and [20]'s risk analysis; the specific worry that "it will save a one-off as a preference" is a plausible instance of [20]'s low-signal filtering rather than a demonstrated result.

- **#24 — Forgetting is a design act, not garbage collection: stores that only grow get slower, more expensive, and less precise; retention windows and a deletion path for withdrawn consent** *(The write path — and forgetting on purpose; Tradeoff ledger).* Supported: **Du et al. 2025** names Forgetting as one of six core memory operations, defined as selectively suppressing memory content that may be outdated, irrelevant or harmful, with time-based deletion and the Ebbinghaus curve among the mechanisms, and distinguishes it from compression [13]; **Du 2026** states plainly that "forgetting is not a bug; it is a feature — essential for robustness, privacy, and efficiency," lists learned forgetting as an open challenge, and notes most systems fail conspicuously on selective forgetting [20]; **MemoryBank** implements a memory-updating mechanism "inspired by the Ebbinghaus Forgetting Curve theory" that forgets and reinforces memory based on time elapsed and relative significance [42]; **GDPR** Art. 17 supplies the legal obligation to erase on consent withdrawal [37]. *Not* supported as stated: the causal chain "slower, more expensive, and less precise." Slower/more expensive is a systems assertion rather than a cited measurement, and — importantly — MemoryBank's own evaluation does not demonstrate that forgetting improves retrieval precision, and [20] notes forgetting is poorly evaluated. The module's "and eventually the agent answers from a memory that should have expired two quarters ago" is illustrative rather than citable.

- **#25 — The ledger tradeoffs: recall precision vs. archive completeness; retention vs. auditability; model-driven extraction vs. deterministic capture; learning vs. stability; acting-now vs. acting-later** *(Tradeoff ledger entries).* The tradeoff *directions* are well supported. Recall precision vs. completeness: [20] measures retrieved-record precision/recall and warns that noise degrades precision; [0] shows distractors specifically cost accuracy. Retention vs. auditability: [37] Art. 5(1)(e) sets storage limitation against Art. 89(1)'s archiving/research carve-out, and **Zep**'s bi-temporal model is explicitly an audit/provenance device that keeps `t'_created`/`t'_expired` even as facts are invalidated [24] — a real instance of the tension. Model-driven extraction vs. deterministic capture: [20] recommends a risk analysis of the write path per domain and [23] shows model-driven operations; [24] shows the reviewer that emerges when extraction is verifiable — Graphiti deliberately prioritises new information when invalidating edges, i.e. the deterministic rule bounds the model. Learning vs. stability: [29], [35], [28] all show promotion improves performance, while [6] warns that writing to procedural memory is riskier than writing to episodic or semantic memory — the tension is real and CoALA states one side of it explicitly. Acting now vs. acting later: no memory-literature source located. *Not* supported: the ledger as such. No located source presents these as a five-entry ledger, and the framing "every fact you store dilutes the next retrieval" inherits the unsupported dilution claim from #19. The ledger is the module's own synthesis instrument.

## Unjustified or novel

- **#5 — The two axes (*what* is remembered vs. *where* it lives), and the claim that conflating them is why "just add a vector DB" fails** *(The memory taxonomy).* *Supported in part:* the second axis has a real literature counterpart — **Du et al. 2025** categorises memory into **parametric** (implicit in model weights) and **contextual** (explicit external data, structured/unstructured) forms [13], which is the module's "in the weights" vs. "in an external store," and it adds the third location the module also names (an external store's *representation*). *Not* supported: the axis-crossing critique. No located source articulates "semantic/episodic/procedural describe *what*; retrieval and parametric describe *where*," nor argues that conflating the axes is why vector-DB-only designs fail. The module also mixes categories within its own second axis — "retrieval" is a *mechanism*, not a location, which is why the module has to say "retrieval and parametric describe *where*." *Novel:* the axes framing, including the diagnosis of the failure mode.

- **#7 — "Procedural memory is not memory at all — it is the instruction"** *(The memory taxonomy, observation 2; the taxonomy table's Procedural row).* **No literature located supports this, and the most directly relevant sources contradict it.** The clearest is an agent-facing survey that maps agent memory onto cognitive mechanisms and defines procedural memory verbatim as "a form of long-term memory dedicated to how to perform tasks" [54]. In cognitive science, procedural memory *is* memory: Squire's taxonomy places skills and habits under **nondeclarative (implicit) long-term memory**, alongside priming and conditioning — it is a memory system, not an instruction set [11], and the declarative/nondeclarative synthesis is built on exactly this architecture [10]. For AI agents, **CoALA** — the module's own cited grounding for the taxonomy — classifies procedural memory as one of the long-term memory modules and defines it as having **two** forms: "implicit knowledge stored in the LLM weights, and explicit knowledge written in the agent's code" [6]. Two consequences the module should absorb: (i) under CoALA the model weights *are* procedural memory, so the module's separate "Parametric" row duplicates CoALA's procedural memory rather than complementing it; and (ii) the prompt/instruction layer is not procedural memory in CoALA at all — it is synthesised per call out of **working memory** [6]. The module's placement of "the instruction" as the procedural-memory store, and its removal of procedural memory from the memory architecture altogether, is a **novel engineering stance**. It is defensible as a design opinion (keep versioned policy in the instruction, not in a searchable archive, because searchable policy drifts), and [6] independently supports the *risk* that motivates it — writing to procedural memory "is significantly riskier... as it can easily introduce bugs or allow an agent to subvert its designers' intentions." But the module states it as a classification fact ("is not memory at all"), which the literature does not support.

- **#10 — Prospective memory: a future task cannot wait inside the conversation, so it must live in a scheduler/queue outside the model; the five-field record (action, trigger, resume state, done flag, approval)** *(Prospective memory: remembering the future).* **Unjustified as a memory-type claim; the scheduler prescription and the five-field record are novel.** The distinction between remembering the past and remembering to perform a future intention is genuine psychology and the module is right to reach for it — Einstein & McDaniel's prospective-memory work establishes the construct and, importantly, the **self-initiated retrieval** problem ([15] is the canonical aging study; [16] the elaboration of self-initiated retrieval processes; [18] is the monograph that treats the field as established). The psychology also endorses *externalising* the intention: it is a distinct construct on a **different axis** from the module's other six — distinguished by temporal *direction* (retrospective vs prospective), not by kind of content — so placing it as a seventh item on the "what is remembered" axis is the module's own move. And the empirical seed of the module's scheduler instinct is genuine: event-based external cues demonstrably outperform internally maintained time-based intentions, and reminders can eliminate interruption costs [55]. So "prospective memory is a distinct thing, it fails by not being initiated, and offloading it to external cues works" is all supported. What is *not* supported: (a) that it is a required **agent memory type**. The field's main agent-memory survey, **"Memory in the Age of AI Agents" [49]**, organises memory as factual/experiential/working and does **not** include prospective memory as a category, and the position paper "Episodic Memory is the Missing Piece for Long-Term LLM Agents" never uses the word. Prospective memory has, however, recently been isolated as an independently measured agent capability — **PM-Bench** [14] evaluates it explicitly (inspired by cognitive science's Virtual Week; best scaffold 65.1% F1), and **TriggerBench** [17] finds it materially harder than retrospective memory, with models overfitting an "always-remind" heuristic. Zhao & Wu's **typed intention store** [50] is the closest published antecedent to the module's design, and reaches 82.9% Set-F1 on PM-Bench by treating PM as "schema-constrained state tracking rather than open-ended reasoning" and putting "lifecycle logic in code" — which is a *research* endorsement of the module's instinct. So the honest state of the literature is: *PM is now a measured capability, not yet a consensus memory type.* (b) The structural argument that "a future task cannot wait inside the conversation" and must therefore live in an external scheduler is an **engineering framing**, correct about stateless inference but not a research finding about memory. (c) The five-field record (action / trigger / resume state / done flag / approval) is **the module's own**, adopted from the practitioner post it cites [36]; no located source specifies this schema. It closely resembles durable-execution and task-queue practice rather than memory research — and note the module's own caveat that the "approval" field is really M15's territory. Two corrections if this is ever cited: **Temporal's own durable-execution documentation documents trigger, resume state, idempotency, and human-in-the-loop approval [51], and in doing so argues *against* the module's necessity claim** — it states that the scheduler-plus-database approach's "complexity isn't necessary with Durable Execution, since you can reliably achieve the same result with nothing more than a for-loop and a sleep statement" [51]. The defensible claim is *durable state external to the model's context, surviving process death*, not *an external scheduler*. (Google Cloud Tasks makes the same point from the other side: idempotency is the handler's responsibility, and task deduplication is retained only ~24 hours.) [51] And the **Saga pattern** is a mismatch — it concerns compensating transactions and says nothing about scheduling future tasks. *Terminological warning:* "prospective" is a false friend in this literature. **RMM's "Prospective Reflection" [21]** means forward-looking *memory construction* (summarising interactions so they can be retrieved later), not prospective memory in the cognitive sense. Do not merge the two.

- **#21 — Fixes must be mechanical (timestamps, consolidation, scoping) rather than prompt-level prose — "prose cannot keep a store correct; policy can"** *(The four failure modes, closing insight).* **No source located.** The literature certainly favours mechanical mechanisms — [24]'s edge invalidation, [23]'s operation set, [20]'s per-user scoping and temporal versioning are all mechanisms, and the memory-security lifecycle analysis [58] argues that persistence, statefulness, and propagation create a threat landscape conventional input-centric controls cannot address, motivating system-level verifiable governance primitives. But no located source asserts the *dichotomy* that prose fixes are ineffective while policy fixes are effective, and the module offers no measurement. This is a normative stance — a reasonable engineering position, and one a course is entitled to teach, but it should be presented as the module's position rather than as a grounded finding. (Its practical corollary, that prompt-level reminders are weaker than harness-enforced policy, is consistent with [58] but is not stated there in these terms.)

- **#26 — The four-failure-mode table as a whole (staleness/contradiction/leakage/recall, each with a fix)** *(The four failure modes).* This is the module's payload, and as a *table* it is the module's own synthesis. The components are each sourced (see #16, #17, #18, #19), but **no located source presents a four-way failure taxonomy of staleness / contradiction / leakage / recall.** Checked and ruled out: the memory-mechanism survey [2] reviews design and evaluation and defines no such taxonomy; **"Anatomy of Agentic Memory" [5]** has two four-way splits, but they are memory *architecture classes* (lightweight semantic; entity-centric and personalized; episodic and reflective; structured and hierarchical) and evaluation/system *limitations* (benchmark saturation, metric validity, backbone sensitivity, latency/throughput overhead) — not failure modes; **"Rethinking Memory" [13]** names six *operations*, not failures; **MAST [30]** is a general multi-agent taxonomy with only two memory-adjacent modes and no memory category; the memory-security literature is attack-centric (poisoning, injection, extraction), a different axis. The closest existing artefact is a striking near-miss: **Governed Shared Memory for Multi-Agent LLM Systems (2026)** does name "four foundational failure modes: unauthorized leakage, stale propagation, contradiction persistence, and provenance collapse," paired with four primitives (scoped retrieval, temporal supersession, provenance tracking, policy-governed memory propagation) [3]. Three of four match — leakage, staleness, contradiction — but the fourth is **provenance collapse**, not recall failure, and its scope is shared multi-agent fleet memory rather than single-agent memory. The module's fourth element (recall failure) is the one the literature does *not* pair with the other three. **Verdict: the four-way taxonomy and its fix column are the module's own construction.** This is not a defect — it is a legitimate synthesis — but it should be labelled as such rather than presented as an established literature taxonomy.

- **#27 — Memory design = "a set of scope, freshness, and retention decisions"** *(Worked example — closing restatement).* The three axes are each individually supported (scope: [27], [20]; freshness: [24], [20]; retention: [37], [13], [42]). *Not* supported: the reduction. No located source defines memory design as the union of these three decision classes, and the definition omits the dimensions the literature treats as equally central — extraction/write-path policy [23], [20], retrieval-method design [25], and representation choice [13]. The definition is the module's own and is narrower than the literature's.

## Where the module conflicts with the literature

Three genuine conflicts, in descending severity.

1. **Procedural memory is classified as "not memory"** (#7). Both cognitive science [10], [11] and CoALA [6] — the module's own cited taxonomy source — classify procedural memory *as memory*, and CoALA further defines the LLM weights as procedural memory and locates the instruction in working memory. The module's taxonomy table therefore both removes a memory type the literature recognises and relocates the weights into a separate "Parametric" row that duplicates CoALA's procedural slot.

2. **"Noise / irrelevant context degrades recall" is backwards as stated** (#19). Cuconasu et al. find that adding **random** documents *improves* accuracy by up to 35%; what degrades accuracy is the retriever's **highest-scoring, semantically related, answer-free** documents [0]. The module's worked-example fix ("pricing is an exact lookup by SKU, not a vector search, so 'find something similar' cannot substitute a neighbouring product's price") is, happily, an instance of the *distractor* problem and is correct — but the general claim that more stored facts dilute retrieval precision is not what this literature shows, and no measurement of an agent memory store's precision-versus-size curve was located. "Lost in the Middle" [1] is also routinely over-read this way: its result is **positional** sensitivity (information at the beginning or end is recalled better than in the middle), not "long or noisy context is worse."

3. **"The model has no reason to doubt its own memory" overstates confident overreliance** (#20). Xie et al. find LLMs can be *highly receptive* to coherent external evidence conflicting with parametric memory, balanced against a strong confirmation bias when evidence partially agrees [32]; Mallen et al. find parametric memory competitive on popular facts, which is why retrieval should be conditional [31]. The module's picture — memory as an unquestioned source of truth — is one end of a two-sided empirical story.

A fourth, softer conflict: the module asserts that recall "gets **worse as you succeed**" because every added fact dilutes the next retrieval (#19). The surveys recommend forgetting and name capacity as an evaluation dimension ([20], [13]) but do not establish the dilution curve, and the module's own cited survey [2] makes no such claim.
